# Explore three.js use-cases

_Ungrilled brainstorm captured 2026-06-20 via a 25-agent exploration workflow. Intent: explore every idea below in depth, one by one, before settling on a set to build. Read PRD.md / CONTEXT.md for site context; this draft is the idea inventory, not a task spec._

# chaipalaka.com — three.js Brainstorm Menu

The catalog converges on three themes that are unusually *native* to this site rather than generic three.js spectacle. **First and biggest: closing the two-RAF gap.** Today the GPU background loop and the CPU matter.js physics loop are strangers — the single most on-brand opportunity is making them talk, either by rendering the live card/tether positions as a GPU SDF metaball field ("the physics, made visible") or by feeding a GPU-computed velocity/layout back into the rope sim. **Second: GPU typography on a text-first site.** Because the prose is the protagonist and `@chenglou/pretext` already lives in the stack, particle/SDF effects that are *seeded by the actual reading content* (a headline that spells itself then disperses, a field that warps around the title, dither that makes prose read as printed) tie spectacle directly to identity instead of bolting it on. **Third: a WebGL layer inside the hero-morph** — the "card expands into a destination" metaphor begs to become a literal portal, though this collides hardest with how the browser View Transitions API actually works (it freezes the old DOM to a static raster, so live WebGL *inside* the morphing pseudo-element is structurally impossible — you'd be replacing the native morph, not augmenting it).

A load-bearing fault line runs through everything: **WebGL2 (today's pinned renderer) vs. WebGPU.** Pure render/shader math — smin SDF, Bayer dither, fat lines, half-float, MRT, GPUComputationRenderer, Data3DTexture volumetrics, setViewOffset, AfterimagePass — all ships on the current `three ^0.184` + `@react-three/fiber 9.6.1` stack with no version bump. Every genuinely-novel *compute* idea (instancedArray storage buffers, `getArrayBufferAsync` readback, atomic spatial-hash) is WebGPU-only, and all of them hinge on one unverified question: **does R3F 9.6.1 even stand up a WebGPURenderer canvas under the vite-react-ssg pins?** Until that's spiked, treat every WebGPU idea as a renderer-integration project, not a scene.

Two cross-cutting corrections worth carrying into any build: (1) **pretext measures block metrics (height/lineCount/maxLineWidth), not per-glyph rects** — every "seed from pretext glyph rects" pitch actually needs `Range.getClientRects` (word-level) or canvas-rasterize-and-sample (glyph-level); and (2) **a fullscreen background quad sits behind the opaque content box**, so any "aura behind the prose" is occluded under the reading column — those ideas want a box-less `/lab` route or a new above-box compositing layer.

## Foreground / cards — bringing GPU into the protagonist physics layer

- **Fat-line tethers** *(start-here)* — `Line2`/`LineGeometry`/`LineMaterial` in a thin ortho overlay; width swells with rope tension, dashes crawl up a taut line, color tracks slack→taut. Feature: WebGL2 fat lines (not the 1px native-line wall, not WebGPU). **Effort: M.** Same A/B-endpoint + slack data `StringLayer.tsx` already computes per frame; SVG paths stay as the no-JS/no-WebGL fallback. Watch: reuse the geometry buffer (no per-frame alloc), track the `resolution` uniform on resize, custom dash-offset uniform for the crawl.
- **Card-aura SDF metaball field** *(strong)* — a 10th fullscreen-quad scene that raymarches each matter.js body center as an `sdSphere`, tethers as `sdCapsule`, `smin`-blended so nearby cards gloop into mercury and split as physics pulls them apart; analytic soft shadows + SDF-AO darken the merge seam. Feature: polynomial smooth-minimum + distance-field soft-shadow/AO (pure GLSL, no dep, no WebGPU). **Effort: L.** Verified the physics layer exposes `body.position.x/y`. Watch: marshal positions across the two RAF loops via a shared ref; cap ~12 primitives; render at reduced internal res (the secondary shadow march ~2× the per-pixel cost); occluded under the content box, so it wants a box-less `/lab` route.
- **Off-axis parallax peephole** *(strong)* — pointer drives a tiny `Camera.setViewOffset` frustum shear so the flat quads gain "fish-tank" depth and look *through* the content box. Feature: asymmetric-frustum sub-rect projection (the frustum-shear-as-window trick almost nobody reaches for). **Effort: S.** Free CPU matrix recompute, no dep, no foreground change. Honest: the illusion is real but quiet — strongest on starfield/lattice (implied z), weakest on flat flow-noise.
- **Celebration shatter** *(worth-exploring)* — Easter-egg burst where a card dissolves into thousands of *distinct* extruded glyph shards via `BatchedMesh` (per-instance cull+sort, one multi-draw), seeded by `MeshSurfaceSampler` from the card's own headline. Feature: BatchedMesh heterogeneous-geometry batching (WebGL2, not WebGPU). **Effort: M.** Watch: Firefox lacks `WEBGL_multi_draw_instanced` and the fast path is emulated (~1.5–2× slower); pretext gives measurement not *outlines*, so you still need a `TextGeometry`/SVG-path extrude step; `build()` is synchronous — run off first paint.
- **Card glyph as figured glass** *(worth-exploring)* — one hero card becomes a `MeshPhysicalMaterial` plane with transmission + dispersion + ior, a planar `Refractor` (cheaper than `CubeCamera` for a flat surface) live-capturing the procedural background; `onBeforeCompile` injects rope-tension stretch. Feature: dispersion (prism-split refraction) + real-time env capture. **Effort: L.** Heaviest single object on the site; knowingly breaks the no-lights/no-3D convention for one object; hide the glass from its own capture via `Object3D.layers`.
- **3D Ladder via CSS3DRenderer** *(worth-exploring → stretch)* — the same card divs get real z via `matrix3d`, commitment-as-depth, staying live accessible DOM. Feature: CSS3DRenderer (DOM-in-3D, no raster, no WebGL). **Effort: L.** The catch the pitch undersells: CSS3DRenderer and matter.js *both want to own the element transform* — reconciling them is a rewrite of the card render path, not an overlay; plus it only honors 100% zoom (an accessibility regression for the audience it courts).

## Deepen ambient backgrounds

- **The field feels the typography** *(strong)* — bake a 2D SDF of the page headline at **build time** (three-mesh-bvh `closestPointToPoint`-as-SDF-generator), ship a tiny grayscale PNG, and warp flow-noise/RD/voronoi around the title at runtime for one extra texture sample. Feature: headless BVH SDF baking. **Effort: M.** Build-time bake dodges runtime cost, WebGL-only-ness, *and* SSR (the warped frame bakes into the same poster). Watch: pretext gives rects not letterform contours — pull glyph outlines from the font, or SDF the coarser rect blocks; keep the new dep build-time-only.
- **Comet-trail / phosphor backgrounds** *(strong)* — route boids + cursor-lattice through `AfterimagePass`; dt-correct and animate the `damp` uniform off scroll velocity (fast scroll → long streaks). Feature: feedback/trail-buffer persistence (a free core addon, not pmndrs). **Effort: M.** Watch: pulls an `EffectComposer` onto the scene (fine, canvas-chunk only); clamp `damp` < ~0.99; half-float target to avoid banding. Note: the "tie to the now-playing beat" embellishment isn't real — that scene's beat is stubbed; scroll velocity is the actually-computable signal.
- **Half-float reclaim + MRT velocity channel** *(worth-exploring)* — flip the verified-`FloatType` reaction-diffusion ping-pong to `HalfFloatType` (perf reclaim), then `count:2` MRT to emit a velocity/gradient field in the same draw. Feature: `WebGLRenderTarget({count})` MRT (the renamed-away-into-invisibility successor to `WebGLMultipleRenderTargets`). **Effort: S.** Real and cheap but it's *plumbing* — payoff deferred until something consumes the velocity channel (see Tether-current). Note the scene is `ShaderMaterial` not `RawShaderMaterial`, so GLSL3 `layout(location)` outputs need `glslVersion: THREE.GLSL3` + hand-managed outputs.
- **House-grade newsprint dither** *(worth-exploring; aesthetically the best fit)* — low-strength ordered Bayer + 2–3-bit posterize as a final pass: risograph texture, banding-killer, dead-on "restrained monochrome / IBM Plex," and the fallback PNG inherits it pixel-identically. Feature: ordered-dither-as-restraint. **Effort: S–M.** Reframe before building: the cited TSL Bayer node is WebGPU-only and pmndrs `EffectPass` is a new dep — **ship a hand-rolled ~10-line GLSL Bayer pass, no dependency.** Chore: re-bake nine fallback PNGs through the same shader.
- **Drifting volumetric fog** *(worth-exploring)* — `Data3DTexture` (64³–128³ worley) marched via cube-backface rasterization, density by scroll depth, pooling against the content-box rect. Feature: the WebGL2-native `webgl2_volume_*` path (no WebGPU — everyone wrongly assumes volumetrics require it). **Effort: L.** Fill-rate-heavy: small texture, capped steps, reduced res. Note: confining fog to the box is an in-shader screen-space test, *not* a `clippingPlanes` job (those are world-space) — the plan conflates the two.
- **Prose floats over water (planar Reflector)** *(stretch — lowest in group)* — a `Refractor`/`Reflector` strip mirrors the background. Mechanically real, but a planar mirror of a *flat fullscreen quad* has nothing with depth to reflect, implies a perspective framing the scenes lack, and is the thinnest identity tie on the board.

## Transitions / motion

- **Guardrail: keep the canvas OUT of the VT snapshot** *(start-here)* — codify (regression test + ADR) why the ambient canvas correctly sits still mid-morph: it's `aria-hidden`, carries no `view-transition-name`, and `preserveDrawingBuffer` is unset, so it never blank-flashes. Feature: the default-canvas-snapshots-blank VT gotcha, documented as intentional. **Effort: S.** Zero risk; protects every ambitious WebGL-in-morph experiment below from silently regressing the core nav into a black flash.
- **Point-cloud gather on ENTER** *(strong — most feasible spectacle here)* — boids/starfield (verified hand-written `ShaderMaterial` Points) get a second position attribute (content-box outline) + a `uMix` uniform mixed in the vertex shader, driven by the morph signal: the field condenses toward the prose, then relaxes. Feature: two-attribute `uMix` morph (sidesteps the r0.184 built-in morph-attribute upload cliff). **Effort: M.** No dep; target shape comes from the same rect the physics walls register. Watch: sync to the browser-owned VT is approximate, not frame-locked; confirm the cloud even mounts on content-box-layout destination routes.
- **Background dissolve matched to the morph** *(worth-exploring)* — `RenderTransitionPass` with `useTexture`/`setTextureThreshold` for a shaped luminance *wipe* (not a flat crossfade) driven by the morph signal. Feature: texture-threshold transition mode (everyone copies the bare slider crossfade). **Effort: L.** Real r184 addon, but needs sceneA+sceneB in one renderer — today each scene is its own `<Canvas>`, so it's effectively gated behind the single-shared-renderer rebuild. (And the "hard swap" premise is already false — a ~300ms cross-fade exists.)
- **One AnimationClip per link-object** *(worth-exploring)* — `AnimationMixer` + `NumberKeyframeTrack` as a generic property scheduler so the PEEK→KEEP→ENTER ladder becomes a `crossFadeTo`-interruptible timeline. Feature: the animation system used as a non-Object3D scheduler. **Effort: M.** The interruptible-gesture goal is genuine, but it mis-models the existing peek/pin motion as "lerps + setTimeout" — much of it is *tested matter.js physics* (the KEEP tether is a real constraint with velocity-driven wobble) a keyframe mixer can't subsume. Could schedule only the discrete non-physical bits.
- *(notable skip)* **GPU N-body layout solver feeding the morph** — WebGPU-only against a pinned stack R3F can't cleanly host, solving a broad-phase cost the CPU demonstrably doesn't have at real card counts (the boids scene already hand-rolls a CPU spatial hash for 5500 pts at 60fps). Novelty without a need.

## New toy-section (`/stuff/*` heavy routes where the 3D *is* the content)

- **Lava — playable physics lava lamp** *(start-here)* — a real matter.js world mirrored 1:1 by a smin-SDF raymarch you drag/fling/cut; bodies physically gloop, tethers become stretching liquid filaments. Feature: smin + analytic SDF shadows/AO, the foreground-physics-made-visible idea as an explicit toy. **Effort: L.** Entirely today's WebGL2 stack, zero new deps, `matter-js ^0.20` already present. The box-occlusion problem vanishes on a dedicated route. Same fill-rate budgeting caveat as the aura.
- **Volume Room — fog cathedral you part** *(strong)* — `Data3DTexture` backface raymarch you scrub by slider; the cursor carves a low-density tunnel. Feature: WebGL2-native volumetrics, self-contained (no matter.js entanglement). **Effort: M.** Genuinely surprising precisely because everyone assumes volumetrics = WebGPU. Only real constraint is the usual fill-rate budget; mild departure in that it needs an actual cube mesh.
- **Dither Press — one-bit risograph print shop** *(strong)* — pipe any of the nine scenes through tunable Bayer + posterize sliders; a "print" button bakes the frame to PNG. Feature: ordered dither as a controllable creative tool. **Effort: S.** Lowest-risk on the board, doubles as the authoring tool for the real house grade. Low novelty ceiling (payoff is a screenshot), but the safest on-brand win.
- **Wordmark Wind Tunnel — type dissolves and re-condenses** *(worth-exploring)* — `GPUComputationRenderer` multi-variable sim, `MeshSurfaceSampler` seeds particles in the glyph shape; word spells itself at rest, goes gaseous on drag. Feature: weighted surface emission + multi-variable coupled GPGPU (all WebGL2). **Effort: L.** Beautiful identity tie, but the pretext→rasterize→sampler→GPGPU seeding chain is more net-new plumbing than "reuse pretext" implies; 250k–1M is a desktop figure — budget tens-of-thousands on the low-power target.
- **Comet Field — feedback-trail playground** *(worth-exploring)* — reuse boids + lattice through `AfterimagePass` with `damp` under the cursor. Feature: feedback persistence as a playable knob. **Effort: S.** Cheapest payoff-per-line, but it's an effect on existing art, not a new world.
- **The Quiet Room — converging studio still-life** *(worth-exploring)* — the anti-shader scene: a few objects accumulate soft contact shadows (`ProgressiveLightMap`), lit by a `RectAreaLight` softbox, ambient-tinted by a `LightProbe` baked from a scene's palette. Feature: in-browser progressive light-map baking + LTC area light. **Effort: M.** Knowingly opts out of no-lights/no-models for one route. **Freshness trap: use the vanilla three addons, NOT drei `<SoftShadows>` — its PCSS broke on three r182 (removed `unpackRGBAToDepth`).** Don't forget `RectAreaLightUniformsLib.init()` or it silently renders black.
- **Portal Slab — punch holes into other scenes** *(stretch)* — BVH-CSG carves apertures showing render-to-texture portals of different scenes. Feature: interactive browser CSG (historically written off as too slow). **Effort: L.** Two pre-1.0 undeclared deps + per-frame CSG re-eval that won't hold 60fps as a *continuous* carve — only a discrete-cut, debounced variant is realistic.

## Text / reading surface

- **Glyph-seeded reaction-diffusion** *(start-here)* — flip the verified `FloatType` RD ping-pong to `HalfFloatType` (perf reclaim) and seed the Gray-Scott field with ink where the current paragraph's rects sit; the pattern germinates from the prose. Feature: half-float feedback buffers + DataTexture seeding. **Effort: M.** Reuses the exact shipped scene; seeding is a write into the existing seed-texture path. Drop the unneeded MRT the pitch borrows; fix the provenance (DOM `getBoundingClientRect`, not pretext).
- **Tether-current: velocity G-buffer nudges the rope cards** *(worth-exploring; best concept-fit, riskiest coupling)* — an MRT velocity channel from the background applies a faint ambient force to matter.js tethers so strung cards drift with the GPU flow. Feature: MRT G-buffer feeding the CPU physics. **Effort: M.** This is the purest "two loops talk" idea, but it pokes the exact footguns this repo has already been burned by: **the `frictionAir` inversion (`frictionAir·dt/16.667 > 2` → NaN)** and a single non-finite rect NaN-poisoning the tether — hard-clamp the force, sanitize the readback, and pipeline it (read frame N-1) or the GPU→CPU stall jitters the 60Hz physics. Touches *every* card, so it must be whisper-faint and tuned solo in-session.
- **Ink-bleed selection** *(worth-exploring)* — a low-strength Bayer halo clipped to the live text-selection rects, so reading leaves a printed wake. Feature: ordered dither + local clipping planes. **Effort: S–M.** The bg canvas is occluded by the content box, so this needs a *new above-box-below-text layer*; cited TSL Bayer node is WebGPU-only (hand-roll GLSL); rects come from `getClientRects`, recomputed per frame.
- **Text-as-particles morph** *(worth-exploring)* — paragraphs dissolve into a `GPUComputationRenderer` cloud and re-condense at the next heading; state in textures survives scroll. Feature: multi-variable GPGPU + vertex-texture-fetch + half-float packing. **Effort: L.** Right renderer, no-JS-safe (real prose underneath), but a from-scratch addon build; the million-point claim won't hold on low-power; "seed from pretext glyph rects" is wrong — raster-sample the text instead.

## Wildcard / cross-cutting

- **Lava-Lamp Ladder** *(start-here)* — the cross-cutting framing of the Card-aura SDF: a 10th scene rendering the live pinned/peeked card field as a lit liquid SDF. Feature: smin SDF + analytic shadows, the signature "two RAF loops finally talk" moment. **Effort: L.** Everything on today's WebGL2 stack, zero deps (drop the optional three-mesh-bvh for v1); only a one-way physics→uniform bridge + fill-rate budgeting stand between it and shipping.
- **Risograph house-grade** *(strong)* — one deterministic dithered grade across all nine backgrounds (hand-rolled GLSL Bayer, no pmndrs). Feature: ordered dither as a house look. **Effort: S.** Highest-certainty win; *strengthens* the no-JS contract (PNG bakes identically); cost is re-baking nine fallbacks.
- **Tethers as living fat lines** *(worth-exploring)* — the cross-cutting version of fat-line tethers: width/dash/color carry rope tension on an overlay canvas. **Effort: M.** Clean DOM-rope fallback; the real work is a coordinate-synced overlay tracking the physics→screen mapping (watch the `resolution` uniform on scroll/resize).
- **The headline that spells itself** *(strong — best of the heavy-spectacle)* — pretext lays out the headline, `MeshSurfaceSampler` seeds a `GPUComputationRenderer` cloud, density-weighted so it's legible at rest and smoke in motion, re-gathering into the next heading. Feature: weighted emission + half-float million-point pattern, **all WebGL2 — no WebGPU/R3F-compat gamble.** **Effort: L.** Degrades to a legible at-rest-title PNG; needs an `EXT_color_buffer_float` capability check; budget particle count for the low-power target.
- *(notable skip)* **GPU spatial-hash that pre-warms the Ladder** — stacks the three most fragile WebGPU corners (atomics, workgroup shared memory, async readback) on an unverified renderer to solve an O(n²) proximity problem the site never has at handful-of-cards scale.

## Start here — prototype these first

These 4–6 balance wow, novelty, and *buildable-today-on-the-pins*:

1. **Glyph-seeded reaction-diffusion (Text, M)** — highest identity payoff for lowest risk: reuses a shipped scene, the half-float swap is per-target one-liners, seeding is a DataTexture write. *First step:* flip the two RD render-target types to `HalfFloatType` and confirm the field still resolves, then wire a paragraph-rect seed write.
2. **Lava-Lamp Ladder / Card-aura SDF (Foreground+Wildcard, L)** — the signature "physics made visible" moment, zero deps, entirely WebGL2. *First step:* build the one-way bridge that snapshots up to ~12 `body.position` values into a uniform array each physics tick, then prototype a 4-sphere smin march at half-res before adding shadows.
3. **Fat-line tethers (Foreground, M)** — makes the rope tension the matter.js sim already computes finally *legible*, drop-in over existing endpoint data, clean SVG fallback. *First step:* stand up the ortho overlay canvas and feed one tether's A/B anchors into a `LineGeometry`, verifying screen-coordinate alignment on scroll first.
4. **Risograph house-grade dither (Ambient+Wildcard, S)** — lowest-risk, highest-certainty, dead-on the brutalist identity, tightens the no-JS contract. *First step:* append a ~10-line GLSL Bayer+posterize block to one scene's fragment shader, then re-bake that scene's fallback PNG through it.
5. **VT guardrail test + ADR (Transitions, S)** — near-zero cost, locks in correct morph behavior and de-risks every WebGL-in-morph experiment. *First step:* write the assertion that the canvas has no `view-transition-name` and `preserveDrawingBuffer` is unset; record the rationale as an ADR.
6. **Off-axis parallax peephole (Foreground/Ambient, S)** — free CPU depth cue, no deps, no foreground risk. *First step:* wire pointer position into a small `Camera.setViewOffset` shear on the starfield/lattice scenes (where it reads best) and tune magnitude small to avoid nausea.

## Big swings — ambitious, know-they-exist even if not now

1. **ENTER as a literal portal** *(XL)* — the card becomes a live window into the destination's world. The dream-fit for this site's whole nav metaphor, but it stacks three compounding hard problems: a router-hoisted renderer (vs. today's per-route lazy chunk, fighting bundle-split), live WebGL inside a browser-VT pseudo-element (**structurally impossible — VT freezes the old DOM to a static raster**, so you'd be *replacing* the native morph), and lossy/experimental DOM-to-texture. A research arc — and the one most likely to black-flash the core nav for everyone if mishandled.
2. **Murmuration / peek-reactive GPGPU flock** *(XL)* — 500k–1M neighbor-aware agents (persistent `instancedArray` storage + atomic spatial-hash) steered by the cursor and the hovered PEEK word. Maximum novelty, but the neighbor-aware core is **WebGPU-compute-only**, the boids scene is CPU today (a from-scratch build, not an upgrade), and the WebGL2 fallback loses exactly the feature that makes it special. **Gate everything behind one spike: can R3F 9.6.1 boot a WebGPURenderer under the pins?** That answer resizes this — and every other compute idea — by an order of magnitude.
3. **Render-persistence across routes** *(XL, enabling infra)* — hoist one renderer above the router so the outgoing frame seeds the incoming scene's intro; the backdrop never cuts to black across a full React/matter.js/card teardown. Worth knowing because it's the *prerequisite* for the matched background-dissolve idea — but note the pitch's premise is partly false (a shared `CanvasLayout` already persists the background within the canvas route group), so the real work is the invasive part: collapsing the per-scene multi-`<Canvas>` fade-swap model into one hoisted renderer that also spans the content-box route group, with mobile context-loss handling.

# Lesser-known three.js features worth knowing
*Curated for chaipalaka.com — three.js ~r0.184 (2026). De-duplicated, grouped by theme. The site runs @react-three/fiber on WebGLRenderer/WebGL2 today (9 ambient background scenes, all 2D-in-camera-space quads/point clouds), with a DOM/matter.js foreground. Tags below flag what fits the current renderer vs. what's a WebGPU/second-renderer opt-in.*

## The dividing line that governs everything
One distinction recurs across the whole catalog and is worth stating once: **on the WebGPURenderer, pure RENDER node-materials/TSL transpile to GLSL on a WebGL2 fallback transparently — but the COMPUTE half (compute shaders, storage buffers, storage textures, atomics, workgroup shared memory) has NO WebGL2 equivalent and simply does not run on the fallback.** So every "novel WebGPU" feature is dual-gated (WebGPU-detect on top of the existing WebGL2-detect) with a no-compute degrade. Two hard facts for this repo: (1) WebGPURenderer *rejects* `ShaderMaterial`/`RawShaderMaterial`/`onBeforeCompile`, so adopting it is additive (a new opt-in route), not a swap of the 9 GLSL scenes; (2) WebGPU/TSL ship *inside* the already-pinned `three` (`three/webgpu`, `three/tsl` subpaths) — **no version bump needed**, which removes the usual blocker. WebGPU is client-only: SSR/no-JS posture (prerendered PNG + gradient fallback, lazy route chunk) is unchanged.

## Rendering & compute (WebGPU/TSL)
*All WebGPU-gated unless noted; opt-in heavy routes only.*

- **Single TSL node graph → dual-backend transpile + node tree-shaking** — Author shading ONCE as a TSL node graph; WebGPURenderer compiles to WGSL (WebGPU) and GLSL (WebGL2 fallback) from one source. Underappreciated: it's the *only* single-codebase path to both GPU APIs with automatic fallback, and because nodes are JS values imported from `three/tsl`, **unused nodes tree-shake out** instead of living in a monolithic shader string — the killer property for a bundle-disciplined site. *Caveat: only the render half transpiles; compute nodes silently don't run on WebGL2.*
- **`instancedArray()` / `attributeArray()` + `SpriteNodeMaterial.positionNode` (persistent-storage GPGPU particles)** — Allocate a GPU storage buffer that PERSISTS across frames; a compute `Fn()` integrates it each frame; the SAME buffer binds as the render `positionNode` — zero CPU↔GPU transfer, state never leaves VRAM. The categorical step up from a stateless point cloud: hundreds of thousands of agents with real per-agent memory (velocity, age, target). *Most demos still wrongly read back unnecessarily.*
- **Storage textures + `textureStore()` / `StorageTextureNode`** — A compute shader WRITES pixels directly by coordinate (`textureStore(tex, coord, value)`), random-access scatter — which fragment shaders structurally cannot do (they only write their own pixel). Replaces ping-pong-render-target (what the site's reaction-diffusion scene uses) with a single in-place compute pass. *Read/write hazards: still need a second texture or barrier for neighbor reads.*
- **Atomic storage ops + `workgroupArray()` / `workgroupBarrier()` (shared-memory compute)** — TSL exposes WGSL atomics (`atomicAdd/Min/Max/exchange`) plus on-chip workgroup shared memory. Lets GPU threads *cooperate and contend* on shared state: histograms, spatial-hash bucket builds, prefix sums, reductions. The deepest, least-tutorialized corner of TSL — even the Maxime Heckel field guide skips it. *Fragile: open three.js issues around atomic assignment/disposal; atomics are 32-bit-int only; easy to write a silent race. Highest debug cost in the catalog.*
- **`renderer.getArrayBufferAsync()` + `ReadbackBuffer` (GPU compute → CPU readback)** — Maps a GPU storage buffer back to a CPU ArrayBuffer after a compute pass; r184-era reusable `ReadbackBuffer` + partial readback avoids per-frame staging-buffer churn. The ONE feature that lets GPU compute feed a NON-GPU consumer — exactly chaipalaka's matter.js+DOM foreground. *Under-documented (most demos never read back); was buggy until ~PR #30132. Async GPU→CPU sync: never await on the critical RAF path — pipeline frame N-1's read while N computes.*
- **`IndirectStorageBufferAttribute` + `drawIndirect` (GPU-driven draw counts)** — A storage buffer whose contents ARE the draw arguments; a compute pass writes `instanceCount` (e.g. from GPU-side cull/compaction) and the draw reads it off-GPU — the CPU never learns how many survived. True GPU-driven rendering: spawn/kill/cull in compute, append survivors, let the GPU decide the count, no readback stall. *Hard WebGPU-only, no WebGL fallback; atomic counter must be 32-bit int; wrong args silently draw garbage.*
- **WebGPU compute atomics for spatial binning / GPU sort** — `atomicAdd` on a 32-bit storage buffer to build a per-frame spatial-hash grid → neighbor queries, the foundation of GPU flocking/SPH/collision at scale. The boundary between "pretty advected noise" and "particles that actually see each other." *No WebGL2 fallback for atomics at all; float accumulation needs fixed-point encoding. Research/AAA territory.*
- **`wgslFn()` raw-WGSL escape hatch** — Wraps hand-written WGSL as a TSL node wired into `colorNode`/`positionNode`/compute graphs — the trapdoor when the JS node API can't express something, or to drop in a published WGSL snippet. Sibling `glslFn()` for the WebGL path. *WGSL → WebGPU-only (won't transpile to WebGL2); every input incl. uniforms must be an explicit param (no implicit capture); #30911-class gotchas with arrays-of-vectors.* **Lowest-risk adoption probe:** port ONE existing GLSL background scene by wrapping its proven noise core in `wgslFn` and only nodifying the plumbing — validates a route can run on WebGPURenderer before a full TSL rewrite.

## Particles & GPGPU at scale (WebGL2-native — fits today's stack)
- **`GPUComputationRenderer` (three/addons) with multi-variable inter-dependent textures** — The classic WebGL2 GPGPU helper: ping-pong float render targets, one per-variable "compute" fragment shader per frame, state lives entirely in textures. The under-used part is the **dependency graph** (`setVariableDependencies()` — velocity reads last-frame position+velocity, position reads new velocity): a full coupled integrator on GPU, the engine behind the official birds/boids and gpgpu_water demos. The only fully cross-browser path to 250k–1M stateful particles with NO WebGPU dependency. *Needs `EXT_color_buffer_float` (universal on desktop WebGL2); cost scales with texture area; adds a second GPU RAF loop.*
- **Half-float / packed multi-attribute state textures + vertex-texture-fetch Points** — The technique that makes a WebGL2 GPGPU sim cheap: hold state in `HalfFloatType` (RGBA16F) not Float32 to halve bandwidth, pack multiple fields per texel (xyz=pos, w=age), and draw 1M points from a *static* BufferGeometry whose only attribute is a lookup UV (a 15-year-old trick newcomers re-discover painfully). The difference between 250k and 1M points at 60fps on a laptop. *Half-float drifts over long sims — keep coords near origin (cf. the matter.js "keep state centered" note). RawShaderMaterial = hand-maintained GLSL.*
- **`BatchedMesh` (many DIFFERENT geometries, per-instance cull + sort, ONE draw)** — Unlike `InstancedMesh` (one geometry repeated), packs MANY distinct geometries into shared buffers, rendered in a single multi-draw with built-in visibility/frustum-cull/back-to-front sort. The right tool for "thousands of little *different* things" (glyph extrusions, card shards, icons). Works on WebGL2 (NOT WebGPU-gated). *Caveat: the fast multiDraw*Instanced path was deprecated; current build emulates it (~1.5–2× slower than true instanced multidraw) and Firefox still lacks `WEBGL_multi_draw_instanced` (#31935). Pre-size max counts.*
- **`MeshSurfaceSampler` (three/addons/math) — weighted O(log n) surface emission** — After an O(n) build, returns weighted random points (with normal/color/UV) uniformly by area, or biased by a vertex weight attribute (`setWeightAttribute('color')` → dense regions emit more, zero-weight faces emit none). The canonical "where do particles spawn FROM" primitive — feed it into an InstancedMesh or a GPGPU sim's seed texture so the cloud is born in the SHAPE of something (a logo, extruded text). *Pure CPU, runs once at init; `build()` is O(faces) and synchronous (do it off first paint). Lives in math/ addons, not the particle docs — easy to miss.*

## Geometry (CPU-side, often headless — feeds the DOM/matter.js foreground)
- **`MeshBVH` (three-mesh-bvh) — `closestPointToPoint` / `shapecast` proximity queries, used HEADLESS** — The de-facto BVH addon. 99% of tutorials use it only as a raycast accelerator; the real power is the **proximity API** — nearest-surface-point + distance in sub-ms, and `shapecast` walking the tree against an arbitrary shape — runnable with NO renderer/scene/canvas, pure geometry math (even in a Web Worker). *Undeclared dep; lazy-chunk behind the WebGL gate even though it needs no GPU.*
- **`MeshBVH.generateSDF` / `closestPointToGeometry` — in-browser SDF baking** — The same library bakes a geometry into a signed-distance field (sample a grid, `closestPointToPoint` per cell → a distance texture for any shader). Most devs don't realize the BVH proximity query IS an SDF generator. *Baking is the expensive step (worker-provided) — or precompute at build time and ship the SDF as a PNG/EXR, fitting the existing prerendered-asset pattern at zero runtime cost.*
- **`three-bvh-csg` (Brush + Evaluator) — real-time boolean geometry** — BVH-accelerated constructive solid geometry fast enough to recompute as operands move (`evaluator.evaluate(a, b, SUBTRACTION)`). Browser CSG was historically slow, so it got written off; few realize 2026-era CSG runs interactively. *Heavy per-frame — handful of low-poly operands only. Two undeclared deps (pre-1.0 — pin against r0.184).*
- **`DecalGeometry` (three/addons) — projected surface geometry** — Generates a NEW geometry that is a box projected/clipped onto a target mesh's surface (graffiti, labels, stamps that conform to curvature). The under-appreciated insight: it's a pure geometry generator, not just a texturing trick. *Needs a target with normals/UVs; distorts at sharp corners; each decal is its own draw call. Presupposes real geometry the site avoids.*
- **`ParametricGeometry` / `LatheGeometry` / `ExtrudeGeometry` with custom `UVGenerator` + bevel/steps/extrudePath** — The procedural constructors, explored past the single-torus-knot demo: parametric u,v→xyz surfaces, profile revolution, and extrude-along-a-path with bevels and your OWN UV mapping. **Footgun:** `ParametricGeometry` moved OUT of core into `three/addons/geometries/` — assuming core silently breaks the build. *All CPU, cheap if built once; deterministic, so good for build-time prerendered-PNG fallbacks.*

## Materials & PBR (WebGL, pinned — no WebGPU)
- **`dispersion`** — Splits refracted light into RGB by wavelength inside the transmission pass, like a prism. Tutorials stop at transmission+ior, so the rainbow fringe is rarely shown. *Transmission needs an extra full render pass — real per-frame GPU cost.*
- **`iridescenceThicknessMap`** — A thin film whose colour depends on thickness, painted per-pixel from a grayscale map (most people set a flat value and never wire the map). *Cheap, no extra pass, but needs an environment map to reflect or it shows nothing.*
- **`anisotropyMap`** — Stretches the specular highlight along a tangent (brushed metal). Silently looks wrong without correct tangents, which keeps it out of tutorials. *Geometry must carry tangents + a real env map or lights.*
- **`MeshMatcapMaterial`** — Fakes a fully-lit surface by sampling one pre-lit sphere image indexed by the view normal — ideal for a site with NO real lights. *Lighting is frozen in view space (highlight sticks as the object spins). Bakeable once at build → doubles as the no-JS fallback.*
- **`onBeforeCompile`** — Splices custom GLSL into a stock physical material (string-replace `#include <chunk>` hooks) while keeping all of three's lighting/fog/tonemapping. The "patch escape hatch": extend a built-in material without rewriting it as a full ShaderMaterial. **WebGL-only, superseded by TSL `colorNode`/`positionNode` on WebGPU — survives here ONLY because three is pinned.** *Brittle (keyed to internal chunk names — re-verify on any three bump); set `customProgramCacheKey` when injected code varies; mutate `shader.uniforms.X.value`, hold the ref (cf. the ShaderMaterial uniform-clone note).*

## Text & typography (SDF/MSDF)
- **`troika-three-text` — on-the-fly SDF/MSDF glyph-atlas text** — The de-facto high-quality three.js text renderer: parses font files, generates an SDF atlas per glyph on demand, patches any material's shader to sample it → crisp, scalable, shader-deformable type with kerning/ligatures/bidi. The most overlooked SDF instance in the whole raymarch/SDF vein (people think "SDF" → blobs, forgetting the most shippable distance-field tool is a TEXT renderer). *External dep; WebGL (worker fallback for atlas gen, no WebGPU needed). **Strictly decorative/canvas-layer** — produces NOTHING for no-JS, must NEVER replace prerendered prose. Distinct from @chenglou/pretext: troika RENDERS, pretext MEASURES — don't conflate.*
  - Deep levers: `curveRadius` + `glyphGeometryDetail` (curved SDF text on a cylinder — detail usually skipped → faceted); `textRenderInfo` + `getCaretAtPoint`/glyphBounds (an unused layout *oracle* — data ready after `sync()`).
- **`three-instanced-uniforms-mesh` (`setUniformAt`) — per-instance arbitrary uniforms** — Beyond `setColorAt`: any uniform per instance (letters that lean toward the cursor). *GLSL atlas + UVs.*
- **`TextGeometry` + `FontLoader` — extruded 3D glyphs** — Often misused for body copy; right for a single drop-cap flourish. *CPU-heavy, large JSON font files.*
- **`MSDFTextNodeMaterial` — MSDF via TSL** — *WebGPU-only; opt-out of the pin. Glyph dissolve effects.*

## Post-processing & multi-pass
- **`AfterimagePass` (three/addons) — feedback-damped motion persistence** *(WebGL2)* — A one-uniform pass that blends `damp` (~0.96) of last frame under the new one → exponentially-decaying trails / phosphor wake, without managing your own ping-pong FBOs. Overshadowed by bloom in every tutorial; almost nobody knows three ships a free frame-feedback pass. The real trick is **animating `damp` off an external signal** (scroll velocity, the /api/now-playing beat) so persistence breathes. *FPS-coupled — dt-correct it or trails differ at 144 vs 30 Hz; clamp `damp` < ~0.99 or it never clears; half-float RT to avoid 8-bit banding accumulating; tints the WHOLE composer, not selected objects. No drop-in Afterimage TSL node in r184 (verify).*
- **MRT — `WebGLRenderTarget({ count: N })` + GLSL3 `layout(location)` outputs** *(WebGL2)* — Render once, write N textures in ONE draw (color + normals + velocity + id). The infrastructure under every depth/normal effect (AO, SSR, motion blur, edge-outline). **The class was invisible-by-rename:** the old `WebGLMultipleRenderTargets`/`WebGLMultisampleRenderTarget` were folded into `WebGLRenderTarget`'s `count`/`samples` props (removed r162) — so most online examples are stale and people never learn `count` exists on the RT they already use. *Needs GLSL3 (`glslVersion: THREE.GLSL3`); each target is real VRAM (use smallest formats: RG16F velocity, RGBA8 ids); WebGPU expresses it through TSL MRT nodes (different code).*
- **`HalfFloatType` feedback (RGBA16F) ping-pong** *(WebGL2)* — Switch simulation-state RTs from `FloatType` to `HalfFloatType`: half the bandwidth/VRAM, far more universally renderable on integrated/mobile GPUs where 32F renderbuffers silently fail. The reflexive `FloatType` default is overkill for color/concentration/trail fields (which need ~3 digits, not 23-bit mantissa). *NOT for accumulating world-space positions over thousands of frames (drift).*
- **pmndrs/postprocessing `EffectPass` effect-merging** *(WebGL, extra dep)* — Architecturally different from three's `EffectComposer`: `EffectPass` MERGES many effects' `mainImage` functions, uniforms, and blends into ONE fullscreen shader (bloom + vignette + noise + tone-map in a single pass over a single buffer). Teams adopt the lib for its bloom and never learn the merge model — the actual perf story. *Convolution effects (SMAA) and UV-transform effects (Pixelation) don't merge — split them. pmndrs' own 2026 guidance is to use TSL/RenderPipeline for WebGPU.*
- **pmndrs `SelectiveBloomEffect` — glow CHOSEN objects, not a brightness threshold** *(WebGL, extra dep)* — Bloom restricted to an explicit Selection set, regardless of frame brightness — the difference between "everything shiny" and "this ONE thing is the light source." Default `UnrealBloom` is so ubiquitous people forget bloom can be authored per-object. *Stateful selection sync; pairs with `layers` (below).*
- **TSL `bayer` dithering node — ordered dither + posterize on output** *(TSL/WebGPU-natural; replicable in raw GLSL)* — A first-class 4×4/8×8 Bayer-matrix node for structured-noise quantization → controlled 1-bit / limited-palette / newsprint-halftone that stays crisp. Counterintuitive as a *restraint* tool: at low strength it's a banding-killer for clean monochrome gradients (dead-on for "restrained brutalism, mostly monochrome, IBM Plex" — makes backgrounds feel *printed*). *Must be applied in the right color space (after tone-map, at 8-bit output). Most devs hand-copy a GLSL snippet and never learn three ships the node.*
- **`GTAOPass` (WebGL) / `GTAONode` (WebGPU TSL) — Ground-Truth Ambient Occlusion** — Horizon-based AO, far closer to reference path-traced AO than the blobby classic `SSAOPass` it (and `HBAOPass`) replaced. The single cheapest "this looks rendered, not flat" upgrade, routinely skipped. **Also covers pmndrs `N8AO`** (quality presets, `halfRes`). *Both consume depth+normals (presuppose the MRT G-buffer) — do nothing on a bare full-screen quad with no geometry depth; order matters vs. SSR.*
- **`RenderTransitionPass` (three/addons) — texture-threshold dissolve** *(WebGL2)* — Renders two scene+camera pairs into HalfFloat RTs and cross-blends. The under-used lever is NOT the linear `setTransition(0..1)` crossfade everyone copies — it's `useTexture(true)` + `setTextureThreshold(t)`, a **luminance-driven WIPE** where a noise/gradient/SDF map decides per-pixel which scene wins → ink-bleed, erosion, shaped reveals. Driving the threshold off a *measured* value (scroll, settle energy) instead of a clock is essentially never done. *~2× GPU during the transition window only.*
- **`RenderPipeline` (the r183 rename of `PostProcessing`) — node-graph WebGPU post-processing w/ WebGL2 fallback** — A DAG of TSL passes (branching, shared intermediate buffers) authored in JS, compiling to WGSL + GLSL. **The rename is itself the obscurity:** nearly all existing code/SO answers still say `EffectComposer`/`PostProcessing`, and most devs don't realize the WebGPU path is a different graph-shaped API, not a renderer swap under the same composer. **`setMRT({ output, normal, depth })`** makes one geometry pass emit a multi-channel G-buffer downstream effect nodes sample — collapsing N passes into a deferred G-buffer in ~10 lines. `EffectComposer` has NO migration path to it (WebGL-only legacy). *Committing to it = committing to WebGPURenderer + TSL; (verify) effect-node maturity (ssr/ao stable vs experimental) in r184.*

## Reflection, refraction, portals & cameras
- **`Camera.setViewOffset` (off-axis / asymmetric-frustum projection)** *(both renderers, ~free CPU)* — Re-derives the projection matrix to render a sub-rectangle of a larger virtual frame. Everyone meets it via the GPU-picking example and never learns the SAME call gives **asymmetric/off-axis frustums for free** — the "shear the frustum so a fixed on-screen rectangle becomes a window" trick (fish-tank VR, convincing 2.5D parallax) that people assume needs hand-rolled `makePerspective()`. *Known r184 gotcha: 1×1-pixel picking mis-samples `THREE.Points` (#31395); `CSS3DRenderer` does NOT honor it (#21723).*
- **`renderer.setScissor` / `setViewport` / `setScissorTest` — multi-region single-canvas** *(both renderers)* — Confine drawing to rectangles of ONE canvas → N independent camera views (split-screen, PiP insets, a magnifier loupe) in one frame, one GL context, one RAF — instead of N renderers each paying full context overhead. *Bottom-left origin (y-flip vs CSS) in DEVICE pixels (×devicePixelRatio — the classic bug); interacts badly with EffectComposer post-passes (#5979).*
- **`CSS3DRenderer` (three/addons) — real DOM in a 3D scene graph** *(no WebGL, tiny bundle)* — Lays out live, selectable, accessible `<div>`s via CSS `matrix3d()` driven by a `THREE.Camera` — crisp vector DOM at any zoom, NOT a rasterized texture. **A near-perfect fit for a site whose foreground is deliberately DOM-not-GPU:** keep gwern-prose text as accessible DOM while giving it real perspective and a camera shared with a WebGL background. *No shared depth buffer with WebGL (fake interleaving via layer ordering); "100% browser zoom only"; load progressively after hydration so no-JS keeps flat-flow DOM; verify it chunks separately from the R3F bundle. (Does not honor `setViewOffset`.)*
- **`CubeCamera` + `WebGLCubeRenderTarget` — real-time per-frame environment capture** *(WebGL)* — Six cameras render the surroundings into a live cube map every frame → dynamic reflections that track motion (not a baked static HDRI). Underused because people don't realize it can capture a *2D procedural* scene just as well as a 3D one. *Six renders/update = expensive (low res, every Nth frame, only on motion); hide the reflective object from its own capture via `layers`.*
- **`Object3D.layers` / `Camera.layers` / `Raycaster.layers` — bitmask pass routing** *(both renderers, zero cost)* — A 32-bit mask routing "render this set in pass A, that set in pass B" WITHOUT separate scene graphs — the canonical enabler for selective bloom, reflection self-exclusion, and per-viewport visibility in scissor setups. Most multi-pass effects that *should* use layers hand-roll `.visible` toggles instead. *Footgun: layer 0 is default-on everything; `.set()` can accidentally drop an object from the default camera. CSS3DRenderer doesn't participate.*
- **`WebGLRenderTarget` portal pattern (+ stencil-buffer alternative)** *(WebGL)* — Render Scene B to a texture, map it onto a quad/frame in Scene A → a literal window into another world; with a viewer-tracking camera it's parallax-correct; attach a `DepthTexture` for depth-correct compositing. R3F users reach for drei's `<MeshPortalMaterial>` and never learn the raw 5-line `setRenderTarget` dance. Stencil alternative: write a per-portal index into the stencil at the aperture and clip the inner scene — true edge clipping, no second target. *One extra scene render per portal (render before the sampling pass); stencil needs careful render-order + ~255 cap. Degrade to the existing per-scene PNG.*
- **`Reflector` / `Refractor` addons (+ `ReflectorNode` for WebGPU/TSL)** — Drop-in planar mirror/refraction meshes with an internal camera + render target → true perspective-correct planar reflections needing NO environment asset (overshadowed by envMap/HDRI in every PBR tutorial; `Refractor` is even more obscure). Cheaper per-mirror than `CubeCamera` for a FLAT surface. *One extra scene render per surface; flat surfaces only; set colorSpace correctly or it washes out. `Reflector`/`Refractor` are WebGL-bound; `ReflectorNode` requires WebGPURenderer (a separate project) — don't pin the design to a renderer you haven't migrated to.*
- **Browser HTML-in-Canvas API (`context.drawElementImage()`) → `CanvasTexture`** *(experimental, browser-native — NOT three.js)* — Rasterizes a LIVE, fully-rendered DOM element (real CSS, fonts, filters) into a canvas at GPU speed → wrap as a `CanvasTexture` and map onto geometry. The long-awaited correct replacement for html2canvas (CSS-subset, no SVG) / SVG-foreignObject (drops cross-origin images, stylesheet styles, unloaded fonts). *Flag-gated, not broadly shipped in 2026 (verify) — treat strictly as progressive enhancement; capture on change, not per frame; the underlying element must stay real DOM for no-JS.*

## Raymarching / SDF / volumetrics
*The thread for chaipalaka: the foreground is already an SDF-shaped problem (matter.js bodies = analytic primitives, Tethers = capsules, the content box = a rounded box) and backgrounds are already fullscreen quads — so an SDF layer can read the SAME body positions the physics loop produces and composite them as a soft metaball field, staying inside the 2D-quad envelope.*

- **Smooth-minimum (`smin`) SDF blending — the metaball operator** *(pure shader math — WebGL2, NO dep, NO WebGPU)* — Instead of `min(a,b)` (hard crease), `smin(a,b,k)` blends distance fields with a smooth, controllable falloff so primitives gloop together like mercury. "Known" in the Inigo Quilez shader-demo subculture but almost never in three.js work — three.js devs default to `MarchingCubes` (geometry, coarse) and never realize the four-line fragment-shader `smin` gives infinitely smooth blends at no triangle cost. Pairs with analytic primitives (`sdSphere`, `sdRoundBox`, `sdCapsule`) and domain ops (twist, repeat). *Cost = primitives × march steps — keep the set ≤~12.* **Runs on the current renderer.**
- **Analytic raymarched soft shadows + AO (from the SDF itself)** *(pure shader math — WebGL2)* — The "second half" of an SDF scene tutorials always omit (they march to a hit, slap on flat color, stop → the plasticky default look). Soft shadows: march one ray toward the light, track min(dist/traveled) → penumbra-correct softness, no shadow map. AO: a few short taps along the normal comparing expected vs actual distance. Nearly unknown outside the demoscene/Quilez lineage. *Only meaningful once an `smin` SDF scene exists; soft shadows ~2× the marching work.*
- **`RaymarchingBox` — three/addons/tsl/utils/Raymarching.js** *(TSL → practically WebGPU today)* — An OFFICIAL but near-invisible addon that generates the fixed-step march loop, ray setup, and box intersection — you write only the per-step body. The sanctioned replacement for the hand-rolled `for(int i...)` every tutorial copy-pastes; people reach for `three-raymarcher` or raw GLSL instead, not knowing three SHIPS a tested loop primitive. *Node-material path reliably exercised only on WebGPURenderer in r184; (verify) the young `{positionRay}` callback signature against the pinned build.*
- **WebGL2 `Data3DTexture` + bounding-box backface raymarch (the `webgl2_volume_*` path)** *(WebGL2-native — fits today's renderer)* — Upload a 3D field into a `Data3DTexture`, rasterize the BACKFACES of a unit cube to launch fragment work only where the volume is, step a ray accumulating density. The highest-fit volumetric option here because it needs **no WebGPU**. Underused because everyone now assumes "volumetrics = WebGPU" and skips the perfectly-good WebGL2 path, and because `Data3DTexture` (vs the familiar 2D `DataTexture`) + the backface-bounding trick are unfamiliar. *3D-texture sampling × steps is fill-rate heavy — keep texture 64³–128³, cap steps, reduced resolution. (verify exact example filename.)*
- **`MarchingCubes` (three/addons/objects) — GENUINE-geometry metaballs** *(WebGL, NO WebGPU)* — Voxelizes a scalar field and triangulates an isosurface every frame → real mesh blobs that participate in depth/occlusion, cast shadows, composite with normal meshes — the niche fullscreen raymarchers can't fill. The 2026 move is constraining it to a thin slab / near-ortho view so it reads as a 2D gooey-merge — exactly this site's camera regime. *Field cost ~resolution³ (keep grid ~28–48 or a flat slab); introduces real 3D geometry + needs a light → knowingly OPTS OUT of the "no models/lights/perspective" convention. Prefer fullscreen `smin` everywhere a single lit moment isn't the point.*
- **`three-good-godrays` — screen-space raymarched volumetric light** *(pmndrs postprocessing EffectPass, WebGL, extra dep)* — Marches each pixel's ray back toward a light sampling the shadow map → true volumetric shafts that respect geometry, vs the built-in `webgl_postprocessing_godrays` radial-blur fake everyone copies (works only for an on-screen light). *Needs the pmndrs lib AND a shadow-casting light + shadow map (collides with "no lights"); per-pixel march × shadow sample is expensive. (verify peer-dep range against r0.184.)*

## Lighting & faux global illumination
*Cinematic light without a forward-lit 3D scene; all opt-in heavy routes — the DOM Cards (CSS) get none of this.*

- **`ProgressiveLightMap` / `ProgressiveLightMapGPU` (three/addons/misc)** — A runtime, in-browser accumulation lightmap baker: jitter the lights, progressively average soft shadows + bounce-ish AO into a lightmap over N frames, converge to a baked-looking surface that costs **zero thereafter**. Hardly anyone knows three ships an in-browser baker (drei wraps it as `<AccumulativeShadows>`, hiding the vanilla addon). *WebGL fine; the GPU sibling needs WebGPU. Requires a 2nd UV set per mesh (authoring tax); front-loaded convergence cost competes briefly with the physics RAF — budget as one-time warmup.*
- **`<AccumulativeShadows>` / `<RandomizedLight>` (drei) + the PCSS `<SoftShadows>` caveat** — The r3f wrapper of the above, specialised to a ground plane → buttery contact-hardening shadows, zero runtime cost once converged. `<SoftShadows>` instead injects PCSS into three's shadow chunk for *dynamic* soft shadows. **LIVE TRAP given the pinned three:** drei `<SoftShadows>`' PCSS broke on three r182 (three removed `unpackRGBAToDepth`) → a naive drei+latest-three combo errors at shader compile; pin compatible versions or use the patched drei (pmndrs/drei #2583). *Object must be static during accumulation (your foreground is animated → this is a separate still 3D layer, not the Cards).*
- **`RectAreaLight` + `RectAreaLightUniformsLib` (WebGL) / `RectAreaLightTexturesLib` (WebGPU)** — A physically-plausible area light (window/softbox) via LTC, producing correct soft falloff and elongated specular streaks off the rectangle's shape — the "cinematic product-shot" look the web almost never has. **The one core light that needs an explicit addon `init()` to work at all** → silently does nothing for people who skip it, who then conclude it's broken. *No shadow casting (pair with accumulative shadows); Standard/Physical materials only.*
- **`LightProbe` + `LightProbeGenerator.fromCubeRenderTarget`/`fromCubeTexture`** — Diffuse irradiance as 3rd-order spherical harmonics — an env map compressed to 27 numbers, ~90% of the diffuse ambience at near-zero per-frame cost vs a full HDRI's memory + PMREM prefilter. The capture-from-CubeCamera path (a probe reflecting actual page colors) is especially obscure. **The 9 SH coeffs are trivially serialisable → precompute at build time, ship as JSON, so the *lighting itself* survives into no-JS/SSR as static data.** *Diffuse only (combine with PMREM for specular); bake once.*
- **`PMREMGenerator` + `scene.environment` / `environmentIntensity` / `environmentRotation` (IBL without an HDRI download)** — Prefilters an environment into a roughness-stratified mipmap for correct image-based diffuse AND glossy lighting. The under-used trick: the source need NOT be a multi-MB `.hdr` — PMREM-prefilter a *procedural* scene (a RoomEnvironment, a gradient, one of your own GPU shaders rendered to a cube) → coherent reflections for kilobytes and zero network, a real win for a strict-bundle, no-HDRI site. *One-time GPU prefilter cost (dispose the generator); Standard/Physical only. (verify `environmentRotation`/`environmentIntensity` are current r0.184 names.)*
- **`SSGINode` (three/addons/tsl/display) — WebGPU/TSL screen-space GI + AO** — A brand-new official node computing real-time screen-space GI AND AO from depth/normal/color (one indirect bounce of color bleeding + contact darkening, no baking, no light setup). The genuinely-modern 2025/26 addition to this vein. *WebGPU-ONLY, heavy (`sliceCount*stepCount` blows up on a laptop iGPU), almost no tutorial coverage — reserve for one flagship WebGPU-required route with a GTAO/baked WebGL fallback.*

## Motion, transitions & timelines
- **`CatmullRomCurve3` + `getPointAt` (arc-length) + Frenet/ahead-point look target, scroll-parameterized** *(pure CPU, ~free)* — A spline camera done correctly. The under-used method is **`getPointAt(u)` NOT `getPoint(t)`**: `getPointAt` reparameterizes by ARC LENGTH so equal scroll deltas move equal *distances* even where control points bunch — the single most common spline-camera bug (cameras lurch, people blame easing). A second sample at `u+0.02` is the lookAt target; `computeFrenetFrames()` (documented only as a TubeGeometry internal) gives full orientation. *OPTS OUT of the "no perspective camera" convention — a new-capability route. Long curves need higher `arcLengthDivisions` (default 200).*
- **`AnimationMixer` + `NumberKeyframeTrack` as a generic property scheduler** *(CPU, tiny)* — three's animation system is really a general keyframe ENGINE (linear/cubic/discrete interpolation, blending, weighting, crossfade, time-scaling) — the property binding is a **string path to ANY object**, not just Object3D transforms. A `NumberKeyframeTrack('.someUniform.value', …)` schedules shader uniforms / a transition threshold on a real, scrubbable, *interruptible* timeline (`crossFadeTo`) — replacing a pile of hand-rolled lerps + setTimeout chains. Almost unheard-of as a non-mesh timeline. *Stringly-typed (silent no-op on a wrong path); tear down on unmount (`stopAllAction`).*
- **GPU geometry morph/dissolve — DataTexture-backed morph attributes (+ the two-attribute ShaderMaterial alternative)** *(WebGL2)* — Built-in morph targets upload as DataTextures and blend on the GPU via `morphTargetInfluences` (scatter→assemble by animating influences 0..1, no per-vertex CPU work). For large point clouds the idiomatic 2026 path is a custom ShaderMaterial holding both position sets + a `uMix` uniform — the same dissolve, sidestepping the **r0.184 upload cliff** where the renderer iterates the whole morph ArrayBuffer (~16ms for big geometries, #26692). Pigeonholed as facial-blendshape tech; rare for abstract point-cloud assembly. *chaipalaka already ships custom ShaderMaterials → the two-attribute pattern is a natural extension.*
- **Cross-route `WebGLRenderTarget` persistence via a single hoisted renderer** *(WebGL2)* — Keep ONE renderer (+ its RTs) alive ABOVE the router so it survives route changes; render route A's final frame into an offscreen RT and seed route B's intro shader with that texture (`setRenderTarget` / `readRenderTargetPixels`, or R3F `useFBO`). The enabling fact — a render target is just a texture you can carry across an unmount if the renderer outlives the route — is under-appreciated (people assume the GL context dies with the page component). *Fights the bundle-split rule: the persistent renderer must live in a route-group layout that only mounts on canvas-bearing routes, never globally. Mobile context-loss can drop the carried texture.*
- **Coupling WebGL with the View Transitions API (`preserveDrawingBuffer` vs explicit captured-frame texture)** *(WebGL2)* — A default WebGL canvas snapshots BLANK into `::view-transition-old` (its drawing buffer is cleared after compositing). Fix: `preserveDrawingBuffer: true` for the transition window only — or better, name the canvas and capture its frame into a texture at transition start to control the cross-fade curve yourself. **The verified takeaway for chaipalaka is the inverse guardrail:** because the ambient canvas is currently UNNAMED and unsnapshotted, it correctly sits still and does NOT flash blank mid-morph — document that as intentional so a future `preserveDrawingBuffer` change doesn't silently regress the hero morph into a black flash. *`preserveDrawingBuffer` has real per-frame cost (enable only during the window); VT pseudo-element tree is FLAT (3D-transform/clip needs nested view-transition-groups); (verify) Firefox VT status mid-2026 — keep the plain-client-nav fallback.*

## Rare core APIs & creative-coding plumbing (WebGL2, pinned — verified against the existing geometric-reaction-diffusion ping-pong)
*The project already runs a manual FloatType WebGLRenderTarget ping-pong GPGPU pipeline but uses NONE of these — genuine leftovers, not duplicates.*

- **GPU color-id picking (hidden id-pass + `readRenderTargetPixels`)** — three.js ships NO core GPUPicker — the canonical "famous technique with no official class" (lives only in third-party repos). Render a second pass with each pickable object flat-colored by its integer id, then read a 1×1 pixel at the cursor and decode → O(1) regardless of object count, pixel-perfect on arbitrary shapes where a CPU raycast against bounding volumes is wrong/expensive. *Full extra render pass (cheap for tiny scenes); the readback is a GPU→CPU stall (do it on pointer events, not per frame); y × devicePixelRatio footgun. WebGPU `readRenderTargetPixelsAsync` currently returns blank (#31658) — irrelevant here.*
- **`Object3D.onBeforeRender` — per-object, per-camera render-time callback** — Fires right before three draws THAT object, with the ACTUAL camera being used — the lower-level, multi-camera-correct hook that R3F's `useFrame` (which most devs use for everything) only *appears* to equal until you add an off-screen pass. The place for view-dependent uniforms that must stay correct per-pass automatically. *Runs in the render loop — keep allocation-free; fires once per camera the object renders with (a feature, but surprising).*
- **Reversed-Z depth buffer (`renderer.reversedDepthBuffer`)** — The modern, cheaper successor to `logarithmicDepthBuffer`: distributes float depth precision evenly to kill z-fighting at large near:far ratios WITHOUT log-depth's per-vertex/fragment shader cost (which "can degrade performance"). Most content still teaches log-depth. *Only earns its keep with real depth-layered 3D (today's flat quads gain nothing). **Naming trap:** `reversedDepthBuffer`, not `reverseDepthBuffer` (r119→r120 rename). File as the "reach for this, not logarithmicDepthBuffer" note for any future depth-stacked morph route.*
- **Local clipping planes (`renderer.localClippingEnabled` + `Material.clippingPlanes` / `clipIntersection`)** — Per-material world-space planes that discard fragments → a GPU scissor in arbitrary 3D orientation (slice meshes open, reveal cross-sections, mask to a moving rect). The `clipIntersection` union-vs-intersection distinction is almost never used. *World space (transform planes per frame to follow an object); discarded fragments still cost overdraw.* **Site fit:** mirror the content box's four edge coordinates as four clipping planes so a GPU effect renders ONLY within/outside the box's live rect — one source of truth driving both physics walls and the visual clip.
- **`MeshDepthMaterial` / `customDepthMaterial` — override the depth-pass shader independently of the color pass** — Supplies a SEPARATE material used only when the object renders into a depth/shadow target — what makes alpha-tested cut-outs cast correct shadows and a vertex-displaced/discarded surface have a matching silhouette in depth-derived effects. Miss it and your custom material looks right but casts a wrong-shaped shadow — a baffling bug almost nobody traces to "the depth pass uses a different material." *Only relevant once something renders the object into a depth target; keep the depth vertex transform in lockstep with the visible material (maintenance tax). Park as a dependency of any future depth/shadow route.*

## Rabbit holes worth a deep dive
1. **The TSL compute boundary as a producer/consumer bridge to matter.js+DOM.** The genuinely novel thing for *this* site isn't GPU particles — it's `getArrayBufferAsync()` readback feeding GPU-computed layout/proximity results back into the CPU physics loop. Worth a real spike: a `/lab` route where a GPU spatial-hash (atomics) does the O(n²) broad-phase the CPU can't afford, reads bucket counts back, and pre-warms which DOM cards get a PEEK preview. The two-RAF architecture already there is exactly the producer/consumer split. Touches the three deepest, least-documented, most-fragile corners at once (atomics, readback, indirect) — high risk, highest payoff, and the only vein where the GPU and the DOM foreground genuinely talk.
2. **The SDF metaball aura that reads the physics state.** `smin` + analytic primitives + analytic soft-shadows/AO, all pure shader math on the *current* WebGL2 renderer, fed each tick by the matter.js Card centers (spheres) and Tethers (capsules) the physics loop already computes. Cards visibly merge into one liquid blob as they collide and split as physics pulls them apart; a strung tether shows as a thinning liquid bridge. The single highest-fit, zero-new-dependency, no-renderer-change spectacle idea — it makes the two unrelated RAF loops finally one picture.
3. **Build-time-baked lighting/SDF data that survives into no-JS.** Two catalog items quietly defeat the client-only ceiling: a `LightProbe`'s 9 SH coeffs ship as 27 floats of JSON, and a `MeshBVH.generateSDF` field bakes to a PNG/EXR at build time. Both let GPU-derived *data* live in the prerendered/SSR world even though the *render* can't. Worth designing the asset pipeline around: the existing per-scene PNG already proves the pattern.
4. **CSS3DRenderer as the "3D Ladder" for a DOM-first foreground.** The one renderer in the catalog whose whole point is keeping accessible, selectable prose as real DOM while a `THREE.Camera` gives it perspective z-depth — uniquely aligned with the deliberate DOM-not-GPU foreground. A spike on an opt-in mode where PEEK/KEEP/ENTER map Cards to real z-depth (matter.js owns x/y, CSS3D adds z) with no raster, no text blur, and flat-div no-JS fallback intact.
5. **The renamed-API archaeology layer.** A surprising amount of "obscurity" in r184 is pure naming churn: `WebGLMultipleRenderTargets`→`WebGLRenderTarget({count})`, `PostProcessing`→`RenderPipeline`, `reverseDepthBuffer`→`reversedDepthBuffer`, `ParametricGeometry` core→addons, `HBAOPass`→`GTAOPass`. Half the stale Stack Overflow answers and "why doesn't my flag work" traps trace here. Worth a one-page internal cheat-sheet of "what it's called NOW" before adopting any of these — it's the cheapest way to avoid silent build breaks against the pinned three.

# Appendix — raw feature catalog (11 research veins)

_The full per-feature research the menu + glossary were synthesized from: what each feature is, why it is rare, its constraints, and a site-specific seed._

### TSL + WebGPURenderer + compute. In 2026 (three.js ~r0.184) this vein is real and shipping: WebGPURenderer is a single renderer that runs WGSL on WebGPU and AUTO-TRANSPILES the same TSL node graph to GLSL on a WebGL2 fallback (Safari 26 closed the last gap in Sept 2025, so coverage is ~95% WebGPU / 5% WebGL2). The load-bearing distinction the whole vein turns on: pure RENDER node-materials/TSL fall back to WebGL2 transparently, but the COMPUTE half — compute shaders, storage buffers, storage textures, atomics, workgroup shared memory — has NO WebGL2 equivalent and simply does not run on the fallback path. So everything genuinely novel here is dual-gated: WebGPU-detect on top of the existing WebGL2-detect, with a graceful no-compute degrade. Two hard facts to respect against the rest of chaipalaka: (1) WebGPURenderer rejects ShaderMaterial/RawShaderMaterial/onBeforeCompile — any of the 9 existing GLSL background scenes would need a TSL port to share one renderer, so adopting this vein is additive (a new opt-in route), not a drop-in swap; (2) three is pinned by vite-react-ssg peer deps, but WebGPU/TSL ships INSIDE the already-installed three (three/webgpu, three/tsl subpaths) — no version bump needed, which removes the usual blocker. SSR/no-JS posture is unchanged: WebGPU is strictly client-only, so any route using it keeps the existing prerendered-PNG + no-JS gradient fallback and must keep all three/webgpu + three/tsl imports behind the same lazy route chunk that already isolates the canvas code from reading routes. (verify) exact r-number where each API landed if pinning to a behavior; the broad capabilities below are confirmed current for r184/2026.
- **renderer.getArrayBufferAsync() + ReadbackBuffer (GPU compute readback to CPU)** — The WebGPURenderer method that maps a GPU StorageBufferAttribute back to a CPU ArrayBuffer after a compute pass (await renderer.getArrayBufferAsync(storageAttribute)). r184-era three added a reusable ReadbackBuffer and partial-readback support so you are not allocating/mapping a fresh staging buffer every frame. This is the bridge that turns the GPU from a pixel-only device into a general parallel coprocessor whose RESULTS you can read in JS.
  - rare: Almost every WebGPU-compute demo writes results straight back into a render pass (positions in -> sprites out) and never reads anything to the CPU, because readback stalls the pipeline. So the readback path is under-documented and was buggy until ~PR #30132 fixed the map/unmap sequencing. But it is the ONE feature that lets GPU compute feed a NON-GPU consumer — exactly chaipalaka's situation, where the protagonist (Cards) lives in matter.js+DOM, not in the canvas.
  - constraints: WebGPU-ONLY; on the WebGL2 fallback there is no compute, so the readback path must be feature-gated with a CPU code path behind it. Readback is async and incurs a GPU->CPU sync — never await it on the critical RAF path; pipeline it (read frame N-1's buffer while frame N computes) or it stalls. Useless for SSR/no-JS (client-only). Adds three/webgpu to the bundle — keep it in the opt-in route chunk only.
  - site seed: An opt-in /lab route where a GPU compute shader runs a force-directed or N-body layout over hundreds of candidate card-anchor points each frame, then getArrayBufferAsync hands the settled positions back to the existing matter.js loop as tether targets — GPU does the O(n^2) broad-phase the CPU physics can't afford, matter.js still owns the final rope feel. The two-RAF architecture already there (R3F loop + physics loop) is exactly the producer/consumer split this needs.
- **Storage textures + textureStore() / StorageTextureNode (compute writes pixels, not just reads)** — A StorageTexture is a GPU texture a compute shader can WRITE to with textureStore(tex, ivec2 coord, vec4 value), dispatched per-texel via renderer.computeAsync(fn.compute(w*h)). Unlike a render target (written only by drawing geometry), a storage texture is written by an arbitrary compute kernel addressing pixels directly — random-access scatter writes, multi-pass image algorithms, history buffers.
  - rare: The whole ecosystem reaches for the ping-pong-WebGLRenderTarget pattern (which chaipalaka already uses for its reaction-diffusion scene) because that's the only option on WebGL2. textureStore replaces ping-pong with a single in-place compute pass and unlocks scatter writes that fragment shaders structurally cannot do (a fragment shader can only write its own pixel). Most tutorials never mention it; it lives in a couple of Codrops articles and the StorageTextureNode docs.
  - constraints: WebGPU-ONLY (no WebGL2 textureStore) — so this is an upgrade PATH for the existing reaction-diffusion scene, not a replacement, unless you keep the GLSL ping-pong version as the WebGL2 branch. Storage textures generally can't be sampled and stored in the same pass (read/write hazards); you still need a second texture or a barrier for neighbor reads. Client-only; PNG/no-JS fallback unchanged.
  - site seed: Rebuild the GPU reaction-diffusion background as a WebGPU storage-texture variant on the one route that opts into WebGPU: same Gray-Scott feel but in-place, freeing the second render target, and — the new trick — seed the diffusion field from the live text layout. Use @chenglou/pretext's pre-paint glyph rects to textureStore ink into the field where prose sits, so the ambient pattern grows out of the actual reading content instead of being decoupled noise.
- **Atomic storage operations + workgroupArray() / workgroupBarrier() (shared-memory compute)** — TSL exposes WGSL's atomics — atomicAdd/Min/Max/Or/exchange on an atomic-typed storage buffer — plus workgroupArray('type', N) for fast on-chip shared memory within a workgroup, synchronized by workgroupBarrier()/storageBarrier(). Together they let many GPU threads cooperate and contend on shared state: histograms, counters, spatial-hash bucket builds, prefix sums, reductions.
  - rare: This is the deepest, least-tutorialized corner of TSL — even the Maxime Heckel field guide skips atomics and workgroup shared memory. Most 'GPU particle' demos are embarrassingly parallel (no thread talks to another) precisely to avoid atomics. Anything requiring threads to AGREE (counting how many particles fell in a cell, building a spatial grid) needs exactly these primitives, and almost nobody uses them in three.js.
  - constraints: WebGPU-ONLY and the most fragile part of the stack — there are open three.js issues around atomic storage assignment and disposal (verify against the current r184 issue tracker before relying on a specific atomic op). Shared-memory size is small (workgroup limits) and correctness depends on getting barrier placement right — easy to write a silent race. Client-only; no SSR involvement.
  - site seed: A GPU spatial-hash on the /lab route: atomically bucket every floating-card anchor into a grid so the broad-phase for 'which cards are near the cursor / near each other' is O(n) on the GPU, with the bucket counts read back (feature #1) to drive which DOM cards get a peek-preview pre-warmed. Lets the Ladder's PEEK tier feel instantly responsive even with a dense field of pinned cards, without the CPU paying n^2 proximity tests.
- **RenderPipeline (ex-PostProcessing) node graph + setMRT()/mrt() G-buffer outputs** — The node-based post-processing system: a PostProcessing/RenderPipeline (renamed RenderPipeline in r183, so r184 has both names) wraps a pass(scene,camera) whose output is a TSL node you compose effects onto — bloom(), ao(), dof() are TSL functions you mix in JS. setMRT({ output, normal, depth, ... }) makes a single geometry pass emit a multi-channel G-buffer that downstream effect nodes sample, instead of re-rendering the scene per effect.
  - rare: Two reasons it's underused: (a) the entire pmndrs/postprocessing ecosystem is WebGL-era EffectComposer, so most code never touches the node pipeline; (b) MRT specifically is treated as advanced-renderer-internals, yet setMRT collapses N passes into one and gives you a proper deferred G-buffer in ~10 lines of TSL. The rename (PostProcessing->RenderPipeline) also means half the docs/blog posts use a now-aliased name, which obscures it.
  - constraints: The node pipeline runs on WebGPURenderer; on the WebGL2 fallback the TSL effects still transpile (render-side), but you lose any effect that depends on a compute pass. Post FX over a full content route risks the 'canvas code leaking into a reading route' bundle rule — keep it on canvas/visual routes only. Each MRT attachment is real VRAM; a wide G-buffer on a high-DPI fullscreen quad is a perf cost. Client-only; PNG fallback unchanged. (verify) which built-in effect nodes (ssr/ao variants) are stable vs experimental in r184.
  - site seed: On a single flagship visual route, render the background scene with setMRT emitting output+depth+normal, then drive a depth-aware effect (subtle DOF or edge-ink) that respects the content box: cards and the prose box sit at known depths, so the post pass can keep text razor-sharp while the ambient field behind it gets a depth-graded treatment — reinforcing the 'content box is the protagonist floating over the field' hierarchy with one MRT pass instead of manual masking.
- **wgslFn() raw-WGSL escape hatch inside the TSL graph** — wgslFn(`...WGSL source...`) wraps a hand-written WGSL function as a TSL node you can wire into colorNode/positionNode/compute graphs. It's the trapdoor for when the JS node API can't express something (a specific WGSL builtin, a hand-tuned loop, a published WGSL snippet) — you drop to native WGSL for that one function and stay in TSL everywhere else. (Sibling glslFn exists for the WebGL path.)
  - rare: TSL is sold as 'never write shader strings again,' so wgslFn is deliberately downplayed and there are open three.js issues literally asking for more examples (#26600). But it's the pragmatic bridge for a team that already knows GLSL/WGSL: you don't have to relearn every operator as a node to adopt the renderer. Its sharp edge — every input including uniforms must be passed as an explicit parameter — is exactly why people bounce off it.
  - constraints: wgslFn is WGSL, so it only runs on the WebGPU backend — a wgslFn node will NOT transpile to the WebGL2 fallback (use glslFn or a pure-TSL node for the fallback path, or accept the route is WebGPU-only). All inputs must be passed as function params (no implicit uniform capture) — known #30911-class gotchas with arrays-of-vectors (verify current status). Client-only; no SSR impact since it's runtime shader code.
  - site seed: Port ONE of the 9 existing GLSL background scenes (e.g. the flow-noise or voronoi quad) to the WebGPU renderer with minimal risk by wrapping its proven GLSL/WGSL noise core in wgslFn and only nodifying the plumbing — a low-cost way to validate that a route can run on WebGPURenderer end to end before committing to a full TSL rewrite of the scene library. De-risks the 'is this vein worth adopting' question with one scene.
- **Persistent-storage GPGPU particles: instancedArray()/attributeArray() + SpriteNodeMaterial.positionNode** — The idiomatic r184 GPGPU pattern: instancedArray(count,'vec3') (or attributeArray) allocates a GPU storage buffer that PERSISTS across frames; a compute Fn() integrates it each frame (read buffer.element(instanceIndex), write back); then the SAME buffer is bound as a SpriteNodeMaterial/InstancedMesh positionNode for rendering — zero CPU<->GPU transfer, simulation state never leaves VRAM. Fn/If/Loop/Break give real control flow inside the kernel.
  - rare: chaipalaka already has a boids scene (~5500 pts) but as a render-only point cloud; the persistent-storage compute pattern is a categorical step up — state lives in a storage buffer and is integrated by a compute pass, so you get hundreds of thousands of agents with real per-agent memory (velocity, age, target), not a stateless reprojection. The 'buffer is both compute output AND render input, never round-tripped' idea is the part most demos still get wrong by reading back unnecessarily.
  - constraints: Compute side is WebGPU-ONLY; the WebGL2 fallback must degrade to the existing simpler/stateless particle scene (or the prerendered PNG). Buffer disposal/leak issues exist in the node system (verify against r184 issues before shipping long-lived buffers). instanceIndex-driven kernels need correct workgroup dispatch sizing. Client-only; the no-JS/PNG fallback already in place covers it.
  - site seed: Promote the existing boids background, on its route only, to a persistent-storage GPGPU flock whose attractor is the cursor AND the live word being hovered for a PEEK — particles drift toward the glyph rect (from pretext measurement) the moment a link is hovered, giving the Ladder's peek tier an ambient 'the field notices what you're about to open' cue, then disperse on dismiss. WebGL2 visitors get the current calmer boids; WebGPU visitors get the reactive upgrade.
- **Single TSL node graph -> dual backend (WGSL/GLSL) transpile + node tree-shaking** — The structural feature underneath the whole vein: you author shading ONCE as a TSL node graph (positionLocal, time, mix, mx_noise_float, Fn, If, Loop) and the WebGPURenderer compiles it to WGSL on WebGPU and to GLSL on the WebGL2 fallback from the same source — and because nodes are JS values imported from three/tsl, unused nodes tree-shake out of the bundle rather than living in a monolithic shader string.
  - rare: It's hidden in plain sight: everyone discusses TSL as 'nicer shader syntax' and misses that it is the only path to a SINGLE codebase that targets both GPU APIs with automatic fallback — the alternative is maintaining parallel GLSL and WGSL by hand. The tree-shaking angle is almost never mentioned, yet for a bundle-discipline-obsessed site it's the killer property: import only the nodes a scene uses.
  - constraints: Only the RENDER half transpiles to WebGL2; compute nodes have no GLSL target and silently don't run on fallback (the dividing line that governs every other feature here). Adopting it for the existing 9 scenes is a real porting cost — ShaderMaterial/onBeforeCompile are unsupported on WebGPURenderer, so each scene must be rewritten in nodes (or wrapped via wgslFn/glslFn). The transpiler occasionally diverges between backends — verify a scene renders identically on both before shipping. three/tsl is a subpath of the already-pinned three, so no version bump; just keep it in the lazy route chunk to honor the reading-route bundle rule.

### GPU particles & GPGPU at scale — state-in-textures FBO sims, WebGPU compute (TSL instancedArray/storage), GPU-driven indirect rendering, and batched/instanced draw consolidation, for three.js r0.184 in 2026.
- **GPUComputationRenderer (three/addons/misc/GPUComputationRenderer.js) with multi-variable inter-dependent textures** — The classic WebGL2 GPGPU helper: it allocates RGBA-float render targets, double-buffers each as a ping-pong pair, and runs a per-variable fragment 'compute' shader each frame so particle state lives entirely in textures (positionTexture, velocityTexture, ...). The under-used part is the multi-variable dependency graph: you call setVariableDependencies() so velocity reads last-frame position AND velocity, position reads new velocity, etc. — a full coupled integrator on GPU with zero CPU per-particle work. The output render targets feed a Points/InstancedMesh vertex shader via vertex texture fetch (each vertex reads its texel by an a_reference UV).
  - rare: Every tutorial stops at a single position texture advected by curl noise. The dependency-graph feature (>1 coupled variable, where one variable samples another's CURRENT frame and a third's PREVIOUS frame) is what the official birds/boids and gpgpu_water demos use, but almost nobody writes by hand — they reach for a library or a single-pass hack. It is the only fully cross-browser path to 250k-1M stateful particles with NO WebGPU dependency.
  - constraints: WebGL2-only addon (pure r184, no toolchain bump needed — does NOT require three/webgpu). Needs EXT_color_buffer_float for float render targets (universal on desktop WebGL2 in 2026; absent on some old mobile GL). Cost scales with texture area, not visible particles — a 1024x1024 = ~1M elements pass is several FBO draws/frame. SSR/no-JS: must lazy-chunk and gate behind the existing WebGL2 detect, ship the prerendered PNG fallback; it can NEVER run prerender-side. Adds a SECOND GPU RAF loop alongside your R3F background loop — budget for it.
  - site seed: A dedicated opt-in 'reading-room' background where the prose's measured glyph rects (you already use @chenglou/pretext for canvas text measurement) seed a position texture: characters of the current paragraph 'dissolve' into a 200k-point cloud that advects on curl noise and re-condenses into the next heading. State held in textures means the morph survives scroll without re-seeding. Stays WebGL2, so it respects your three-pin and bundle-split rules.
- **TSL compute: instancedArray() + storage() + Fn().compute(count) on WebGPURenderer** — The 2026 WebGPU-native replacement for FBO ping-pong. instancedArray(COUNT, 'vec3') allocates a persistent GPU storage buffer (a StorageInstancedBufferAttribute under the hood) that survives across frames; a Fn() compute kernel indexed by instanceIndex reads/writes buffer.element(instanceIndex); you dispatch with renderer.computeAsync(kernel.compute(COUNT)). No render-target round-trip, no texel packing, no power-of-two texture sizing — particle state is just a typed array on the GPU you mutate in place, then bind the SAME buffer as a vertex attribute for drawing (zero copy).
  - rare: Most three.js code in the wild is still WebGL/GLSL; the storage-buffer compute path only became production-ready around r171 (late 2025) and the docs are thin. The genuinely under-appreciated wins: (1) you can keep struct-of-arrays buffers for position/velocity/age separately and never pack into RGBA; (2) the same TSL Fn compiles to WGSL on WebGPU and GLSL on the WebGL2 fallback for the RENDER side, so only the compute step is WebGPU-gated; (3) curl-noise advection is a few lines of TSL node math instead of a hand-written shader string.
  - constraints: Compute shaders and StorageBufferAttribute 'can only be used with WebGPURenderer and a WebGPU backend' — the WebGL2 fallback renderer does NOT run compute, so you need a real fallback path (e.g. GPUComputationRenderer or a static cloud) for it. CRITICAL for this repo: requires importing from three/webgpu (WebGPURenderer + TSL), which is a heavier entry point than your current background scenes use; whether @react-three/fiber's WebGPU canvas works under your PINNED three/r3f versions without a bump is the open question — treat adoption as its own project, not a drop-in (verify against the vite-react-ssg three pin before committing). WebGPU is broadly available in 2026 (Chrome/Edge/Firefox desktop, Safari 26) but still absent on older Safari/locked-down browsers, so the detect+fallback is mandatory. Compute never runs at prerender/no-JS time.
  - site seed: An opt-in /lab or single hero route that pushes 500k-1M curl-advected points reacting to cursor — a spectacle ceiling your current CPU-matter foreground can never reach. Because only the compute dispatch is WebGPU-gated, the no-WebGPU path can degrade to the existing GPUComputationRenderer scene at lower particle count, keeping a single visual language across backends.
- **IndirectStorageBufferAttribute + drawIndirect (GPU-driven draw counts)** — A storage buffer whose contents ARE the draw arguments (vertexCount, instanceCount, firstVertex, firstInstance). A compute pass writes those numbers — typically an instanceCount produced by GPU-side culling/compaction — and the draw call reads them straight off the GPU, so the CPU never learns how many particles survived. This is true GPU-driven rendering: spawn/kill/cull particles in compute, append survivors to a buffer, and let the GPU decide the instance count for the same frame with no readback stall.
  - rare: It is the deep end of the WebGPU path that even most WebGPU three.js demos skip — they keep a fixed instanceCount and just move particles off-screen. Compute-written indirect draw counts (the 'append-only survivor buffer + atomic counter' pattern) is the technique that lets particle COUNT itself be dynamic without a per-frame GPU→CPU readback (the thing that otherwise destroys frame pacing). Genuinely advanced and almost never seen on a personal site.
  - constraints: Hard WebGPU-only: docs state it 'can only be used with WebGPURenderer and a WebGPU backend' — no WebGL fallback exists for indirect draws, so this is strictly an opt-in-heavy-route feature behind a WebGPU detect. The atomic counter for compaction must be a 32-bit integer (WebGPU atomics are limited to 32-bit int types). Same three/webgpu + pin-bump caveat as the TSL-compute entry. Useless for SSR/no-JS (compute + indirect both runtime-GPU only). Debugging is harder — wrong indirect args silently draw garbage or nothing.
  - site seed: An 'attention budget' visual: each Ladder PEEK/KEEP card emits a burst of GPU particles, and a compute cull keeps only the N closest-to-cursor alive via an atomic append + drawIndirect — so the on-screen particle population breathes with how many links you are hovering, with the population count decided entirely on-GPU. A flagship for the 'playground, anything goes' route while plain reading routes stay zero-GPU.
- **BatchedMesh (multi-geometry, per-instance frustum culling & sorting in ONE draw)** — Unlike InstancedMesh (one geometry repeated), BatchedMesh packs MANY DIFFERENT geometries into shared vertex/index buffers and renders them in a single multi-draw call, with built-in per-instance visibility, frustum culling, and back-to-front sort. You addGeometry() several shapes once, then setMatrixAt()/setVisibleAt() per instance — ideal when 'particles' are heterogeneous small meshes (glyph extrusions, card shards, icons) rather than identical point sprites.
  - rare: Everyone reaches for InstancedMesh and assumes you must duplicate one geometry; BatchedMesh's killer feature — mixing distinct geometries in a single draw WITH automatic culling and sort — is barely used outside a couple of Codrops articles. It is the right tool exactly when InstancedMesh's single-geometry limit bites, which is most 'thousands of little different things' cases.
  - constraints: Works on the WebGL2 renderer in r184 (NOT WebGPU-gated) — good for your pin situation. BUT: the fast multiDraw*Instanced path was deprecated and the current build emulates instancing by repeating multiDraw params, which is ~1.5-2x slower than true instanced multidraw, and Firefox still lacks the WEBGL_multi_draw_instanced extension (issue #31935 open as of 2026) — so the speedup over many separate draws is real but not maximal, and Firefox falls back hardest (verify the exact perf delta on your target browsers). Requires pre-sizing max vertex/index/instance counts. SSR/no-JS: same lazy-chunk + gated + PNG-fallback discipline as your other scenes; never prerendered.
  - site seed: Replace the DOM-div particle metaphor for a special celebratory state (e.g. an Easter-egg on the content box) with BatchedMesh shards: extrude a handful of distinct glyph/icon geometries once, scatter thousands, let BatchedMesh cull+sort them as they tumble — a foreground GPU layer that coexists with (doesn't replace) the matter.js Cards, only on opt-in routes so reading routes stay pure DOM.
- **MeshSurfaceSampler (three/addons/math/MeshSurfaceSampler.js) — weighted O(log n) surface emission** — A CPU sampler that, after an O(n) build, returns weighted random points (with normal, color, UV) uniformly by area — or biased by a vertex weight attribute — on any mesh surface in O(log n) per sample. It is the canonical 'where do particles spawn FROM' primitive: feed its output into an InstancedMesh matrix list or into the initial position texture of a GPGPU sim so the cloud is born in the SHAPE of something (a logo, extruded text, a glyph mesh) rather than a random box.
  - rare: It lives in the math/ addons folder, not the particle docs, so it is easy to miss; people hand-roll barycentric sampling or scatter in a cube. The weighted-sampling feature (setWeightAttribute('color') so dense regions emit more, zero-weight faces emit none) is especially overlooked — it turns a texture/heatmap into an emission-density field for free.
  - constraints: Pure CPU, pure-r184 addon — no GPU, no WebGPU, no pin concern; it runs once at init, not per-frame. The build() is O(faces) and synchronous, so sampling a very dense mesh can jank the main thread — do it off the first paint or in an idle callback. It only produces SEED points; the actual animation still needs your Points/GPGPU/compute layer (one of the features above). SSR/no-JS: it can run, but pointless without a canvas — keep it inside the lazy-loaded scene chunk, never in the prerender path.
  - site seed: Use pretext to lay out a headline, extrude it (or rasterize to a weighted plane), and MeshSurfaceSampler the glyph surface to seed the initial particle positions for any of the GPGPU sims above — so the cloud literally spells the page title before dispersing on hover. Density-weighting by glyph coverage makes the text legible at rest and gaseous in motion, tying the particle spectacle back to your text-central, gwern-style identity.
- **Half-float / packed multi-attribute state textures + RawShaderMaterial vertex texture fetch (the WebGL2 'no-WebGPU' scaling trick)** — The technique that makes a WebGL2 GPGPU sim cheap: hold particle state in HalfFloatType (RG16F/RGBA16F) render targets instead of full Float32 to halve bandwidth, pack multiple logical fields into one RGBA texel (xyz=position, w=age), and on the render side use a RawShaderMaterial Points whose vertex shader does texture(positionTex, a_reference) — vertex texture fetch — to place each point. The lesser-known levers are the precision/packing choices and using a single static BufferGeometry of UV 'references' instead of streaming attributes.
  - rare: Tutorials default to FloatType everywhere and one field per texture, doubling memory and FBO bandwidth for no reason; half-float state textures and field-packing are the difference between 250k and 1M particles staying at 60fps on a laptop GPU. Vertex texture fetch into a Points cloud (drawing 1M points from a static geometry whose only attribute is a lookup UV) is a 15-year-old trick that newcomers re-discover painfully — and it remains the most compatible million-point path in 2026.
  - constraints: WebGL2 + EXT_color_buffer_float (for renderable half-float targets) — pure r184, no pin bump, no WebGPU. Half-float costs precision: positions drift over long sims, so keep coordinates near origin or periodically renormalize (you have a related matter.js note about bodies near x≈0 — same 'keep state numerically centered' discipline). RawShaderMaterial means you write/maintain GLSL by hand (no node graph). Points sprites get expensive on fill rate at large gl_PointSize — keep sprites small. SSR/no-JS unchanged: lazy chunk, WebGL2 gate, PNG fallback; never prerender.
  - site seed: Make the existing boids/flow-noise ambient backgrounds an order of magnitude denser WITHOUT touching the three pin or adding WebGPU: convert their point clouds to half-float packed state textures + vertex-texture-fetch Points, lifting ~5.5k boids toward 250k-1M while keeping the same per-route lazy chunk, WebGL2 detect, and prerendered-PNG fallback you already ship — a pure scale-up of the current GPU background vocabulary.
- **WebGPU compute atomics for spatial binning / GPU sort (neighbor-aware particles)** — Using atomicAdd on a 32-bit storage buffer inside a TSL compute kernel to build a per-frame spatial hash grid (bin particles into cells), enabling neighbor queries — the foundation of GPU flocking/boids, SPH-style fluids, and collision-aware particles at scale. Atomics let thousands of threads concurrently increment per-cell counters and compute write offsets without races, something WebGL2 GPGPU effectively cannot do (no scatter/atomic writes in a fragment shader).
  - rare: Atomics + GPU spatial binning is the boundary between 'pretty advected noise' (what 95% of particle demos do, including yours today) and 'particles that actually see each other.' Almost no personal site does GPU neighbor search; it is firmly research/AAA territory, and the TSL atomic surface is barely documented in 2026.
  - constraints: WebGPU-backend-only and atomics are LIMITED TO 32-BIT INTEGER types in WebGPU — float accumulation needs fixed-point encoding or a separate pass, which is the main authoring tax. No WebGL2 fallback for atomics at all (the fallback must use a fundamentally different, cheaper algorithm or skip neighbor-awareness). Same three/webgpu import + pinned-version caveat as the other compute entries — confirm the WebGPU renderer path is reachable under your vite-react-ssg pins before scoping (verify). Strictly runtime; irrelevant to SSR/no-JS. Highest implementation/debug cost of anything in this list.
  - site seed: A signature opt-in route where the Ladder's KEEP'd cards exert real flocking influence on a GPU particle field — particles bin into a spatial grid and steer to avoid/orbit the live card positions (fed in from matter.js each frame), so the GPU foreground and the CPU-physics foreground genuinely interact. Maximum novelty, explicitly heavy/experimental, gated hard behind WebGPU with a graceful curl-noise-only fallback — exactly the 'spectacle where fun' carve-out the playground framing invites.

### Post-processing & multi-pass
- **AfterimagePass (three/addons/postprocessing/AfterimagePass.js) — and the hand-rolled feedback/trail-buffer pattern it embodies (TexturePass + SavePass ping-pong)** — A one-line addon pass that blends each frame with a damped copy of the PREVIOUS frame's output (composer-internal ping-pong render targets, a single `damp` uniform ~0.8–0.96). It is the canonical 'trail / persistence-of-vision / phosphor decay' buffer: output(t) = max/mix(input(t), output(t-1)*damp). The same idea generalizes to a manual SavePass→TexturePass loop or a feedback ShaderPass when you want custom decay math (directional smear, hue-rotate-on-decay, additive vs. lighten blend).
  - rare: Nearly every post-processing tutorial stops at bloom/DoF/FXAA. Frame-feedback is skipped because it is stateful (most passes are pure functions of the current frame) and its behavior is FPS-dependent, so people get burned and abandon it. But it is the cheapest way to get 'motion has weight / light leaves a wake' — a fundamentally temporal look you cannot fake with a single-frame shader.
  - constraints: WebGL only as an addon (the WebGPU/RenderPipeline path would need a TSL feedback node, which is more manual — (verify) no drop-in Afterimage node in r184). Needs its own EffectComposer, so it pulls the WHOLE 3D bundle onto a route — a hard violation of the 'no canvas code in plain reading routes' rule, so it stays a background-only effect. `damp` is frame-rate-coupled: trails are longer at 144Hz than 30Hz unless you damp by delta-time; pin or dt-correct it. Float/half-float render targets recommended to avoid 8-bit banding accumulating in the trail. Background-only ⇒ no SSR/no-JS concern (already behind the WebGL2 gate + PNG fallback).
  - site seed: On the boids (~5500 pts) and cursor-repel lattice background scenes, route them through one AfterimagePass so the flock and the grid leave faint comet-trails — turning the existing point clouds from 'static-feeling motion' into something that reads as flow. Tie `damp` to the /api/now-playing beat on the audio-reactive scene: trails lengthen on the downbeat, snap short between beats — a temporal pulse the current single-frame shaders can't express.
- **Multiple Render Targets via WebGLRenderTarget({ count: N }) + GLSL3 layout(location) outputs (note: the old WebGLMultipleRenderTargets class was REMOVED)** — Render a scene ONCE and write N separate textures in a single draw — e.g. gl_FragColor[0]=color, [1]=normals, [2]=velocity/id — by allocating a render target with `count: 3` and emitting `layout(location=0..2) out vec4` in a GLSL3 material. The downstream post pass then reads all N as uniform samplers. This is the infrastructure every 'needs depth+normals' effect (AO, SSR, motion blur, edge-outline) silently sits on.
  - rare: The API moved twice (WebGLMultisampleRenderTarget and WebGLMultipleRenderTargets were both folded into WebGLRenderTarget's `count`/`samples` props), so most online examples are stale and people don't realize MRT is now a one-property flag. Hand-authoring MRT materials is also seen as 'engine internals,' so app devs reach for prebuilt AO passes instead of ever composing their own G-buffer.
  - constraints: Requires WebGL2 (GLSL3 `#version 300 es`, `layout(location)`); the site's WebGL1 fallback path can't use it — gate accordingly. Each extra target is real VRAM/bandwidth, so cap N and use the smallest viable formats (RG16F for velocity, RGBA8 for ids). WebGPU/RenderPipeline expresses the same thing through TSL MRT nodes — different code, so an MRT pass is renderer-specific (verify the exact TSL MRT API for r184 before porting). Background-only by the bundle rule; no SSR/no-JS impact.
  - site seed: The GPU reaction-diffusion scene already does ping-pong render targets — extend it to MRT so a single diffusion pass emits BOTH the chemical concentration AND a derived gradient/normal field, then feed the normal field to a cheap edge-light pass. One draw instead of two, and it unlocks a 'screen-space outline' look on the voronoi/flow scenes that matches the brutalist black-line aesthetic without re-rendering geometry.
- **pmndrs/postprocessing EffectPass effect-merging (single compound fullscreen shader, not an EffectComposer ping-pong chain)** — pmndrs/postprocessing is architecturally different from three's addon EffectComposer: instead of one render-target round-trip per pass, `EffectPass` MERGES many Effects' `mainImage`/`mainUv` GLSL functions, uniforms, and blend functions into ONE fullscreen fragment shader. Bloom + vignette + noise + tone-map can all execute in a single pass over a single buffer.
  - rare: Teams reach for the library to get its bloom and never learn the merge model — they stack many EffectPasses (defeating the point) or assume it's 'just three's EffectComposer with nicer defaults.' The merge is the actual perf story and the reason it scales to many subtle effects at near-zero added cost.
  - constraints: Not all effects merge: a UV-transform effect (Pixelation) + a convolution effect (SMAA) corrupt each other, and two convolution effects can't share one pass (input buffer is read-only mid-pass) — those must be split into separate EffectPasses. WebGL-focused; pmndrs' own guidance in 2026 is to use three's TSL/RenderPipeline post-processing for WebGPU rather than this lib. It's an extra top-level dependency (declare it) and, being canvas code, is background-route-only under the bundle-splitting rule. No SSR/no-JS concern (gated behind the existing WebGL detect).
  - site seed: Adopt one shared EffectPass across ALL nine background scenes carrying a stack of deliberately restrained effects — subtle vignette + film-grain + a whisper of chromatic aberration at the edges + ACES tone-map — merged into a single pass so the cost is one fullscreen draw regardless of scene. This gives every ambient background a consistent 'graded' house look (the brutalist-but-warm tone) for the price of one pass, and centralizes the grade in one place instead of nine bespoke shaders.
- **TSL Bayer dithering node (three/tsl `bayer`/Bayer module) for ordered-dither + posterize on output** — A built-in TSL function that applies a 4x4 (or 8x8) Bayer-matrix ordered dither to a color before quantization — the structured-noise step that lets you crush an image to few colors / few bits WITHOUT smooth-gradient banding. Pair it with a posterize/quantize step and you get a controlled 1-bit / limited-palette / newsprint-halftone look that stays crisp instead of muddy.
  - rare: Dithering is usually hand-copied as a magic GLSL snippet from a blog; few people know three.js ships a first-class TSL `Bayer` node, so it's underused as a composable, renderer-portable building block. Ordered dither is also counterintuitive as a 'restraint' tool — it's associated with retro/loud looks, but at low strength it's actually a banding-killer for clean monochrome gradients.
  - constraints: Lives in the TSL/node world (three/tsl), so it's most natural on the WebGPU RenderPipeline path; on classic WebGL you can replicate the matrix in raw GLSL but you don't get the node. Dither must be applied in the right color space (after tone-map, before/at 8-bit output) or it looks wrong. As a post pass it's canvas/background code — keep it out of reading-route bundles. No SSR/no-JS effect; the PNG fallback can simply bake the dithered frame.
  - site seed: Run a LOW-strength Bayer dither + 2–3 bit posterize as the final node on the monochrome flow-noise and starfield backgrounds: the result is a crisp newsprint/risograph texture that is dead-on for 'restrained brutalism, mostly monochrome, IBM Plex' — it makes the ambient backgrounds feel printed rather than rendered, and kills the 8-bit banding those smooth noise gradients currently show. The prerendered fallback PNG inherits the exact same texture, so JS-on and JS-off look identical.
- **pmndrs SelectiveBloomEffect (selection-mask bloom) — glow only chosen objects, not a brightness threshold** — Bloom restricted to an explicit Selection set rather than the usual luminance-threshold bloom that lights up anything bright. You add specific objects to a Selection; only those emit the glow, regardless of how bright the rest of the frame is. Implemented via a mask/selection render that gates the bloom contribution.
  - rare: Default UnrealBloom is so ubiquitous people forget bloom can be authored per-object. Selective bloom needs a selection-buffer/layer dance that the basic threshold path hides, so most projects either over-bloom the whole scene or skip glow entirely. It's the difference between 'everything shiny' and 'this ONE thing is the light source.'
  - constraints: pmndrs lib (WebGL); declare the dependency. Selection management is stateful and you must keep the selection in sync as objects come and go. The three.js native equivalent (separate-layer bloom + additive composite) is more manual. WebGPU path again wants the TSL/RenderPipeline route. Strictly a canvas effect ⇒ background-only by the bundle rule; the foreground is zero-GPU DOM/matter.js and gets none of this. No SSR/no-JS implications beyond the existing gate.
  - site seed: The site's foreground is DOM cards, not WebGL — so use selective bloom in the audio-reactive background to make ONLY a small set of 'beat marker' points bloom on each downbeat from /api/now-playing, leaving the rest of the field dark. It reads as a single pulsing light source behind the prose instead of a uniformly glowy scene, which suits the quiet, mostly-dark brutalist palette far better than threshold bloom would.
- **RenderPipeline (the r183 rename of PostProcessing) — node-graph, WebGPU-native post-processing with a WebGL2 fallback** — three.js's node-based post-processing system: a DAG of TSL passes (not a linear composer chain) that can branch and share intermediate buffers, authored in JavaScript TSL that compiles to BOTH WGSL (WebGPU) and GLSL (WebGL2). In r183 the class formerly exported as `PostProcessing` was renamed `RenderPipeline` to reflect that it's a pipeline graph, not a single effect — same API.
  - rare: It's brand-new vocabulary (the rename landed in r183), so almost all existing code, tutorials, and Stack Overflow answers still say EffectComposer/PostProcessing. Most devs don't yet realize the WebGPU path is a different, graph-shaped API — not a renderer swap under the same composer — which is exactly why it's underused and worth scouting now.
  - constraints: WebGPU-first; the WebGL2 fallback exists but is the secondary target, and EffectComposer has NO migration path to it (it's WebGL-only legacy). Adopting it means committing to the WebGPURenderer + TSL world, which is a real toolchain decision against the site's pinned three (a renderer/three bump is 'its own project' per the constraints — (verify) confirm r0.184's RenderPipeline maturity before betting a route on it). WebGPU still isn't universal in 2026, so you'd need a WebGL2/no-WebGPU fallback below the existing WebGL detect. Background-only; SSR prerender still needs the PNG/no-JS fallback since none of this runs server-side.
  - site seed: Treat it as the forward-looking migration target for the background-scene subsystem, NOT a today-task: prototype ONE opt-in heavy/experimental route (the 'anything goes' playground license) on WebGPU + RenderPipeline to author a branching graph — e.g. reaction-diffusion feeding both a bloom branch and a dither branch from one source node — proving the TSL-shared-buffer model before any wholesale port. Keep it gated and fallback-backed so the pinned-three reading routes are untouched.
- **pmndrs N8AO (drop-in high-quality ambient occlusion) and GTAOPass (three/addons) — modern AO that actually looks good at low cost** — N8AO is a third-party pmndrs-ecosystem AO effect with quality presets (performance→ultra), a `halfRes` mode, and far better quality-per-millisecond than three's legacy SSAOPass; GTAOPass (ground-truth AO) is the in-tree addon counterpart with similar quality goals. Both consume depth+normals (the MRT G-buffer above) to darken contact creases and add perceived depth/weight.
  - rare: People default to the old SSAOPass (noisy, halo-prone) or skip AO as 'too expensive,' unaware that N8AO/GTAO changed the cost/quality math. AO is also wrongly assumed to need a lit, modeled scene — but it's just a depth+normal post pass, so it applies to procedural/point-cloud scenes too, which almost nobody does.
  - constraints: Both need depth and normal buffers (so they presuppose the MRT/G-buffer feature above) — they do nothing on a bare full-screen-quad shader with no geometry depth. WebGL2 for the good paths; N8AO is an extra dependency (declare it). GTAOPass is an EffectComposer addon (WebGL); the WebGPU equivalent is the TSL AO node. Real per-frame cost even at halfRes — keep it to opt-in heavy routes. Background/canvas only ⇒ excluded from reading-route bundles; no SSR/no-JS path (gated + PNG fallback).
  - site seed: The current 9 scenes are all flat full-screen quads/point clouds with NO depth — so the high-leverage move is to FIRST give one experimental scene real depth (e.g. the boids as small camera-facing instanced quads at varying z) and then drop N8AO/GTAO on it: suddenly the flock has soft contact shadows where points cluster, reading as volume rather than a flat sprite field. ### Raymarching / SDF / volumetrics — fullscreen-quad shader-heavy techniques. The thread connecting the picks for chaipalaka: this site's foreground is already an SDF-shaped problem in disguise (matter.js bodies = analytic primitives, Tethers = capsules, the content box = a rounded box), and its backgrounds are already fullscreen quads. So the highest-leverage rare features are the ones that let an SDF/raymarch layer (a) read the SAME body positions the physics loop already produces and composite them as a soft, metaball-blended, volumetric field WITHOUT introducing models, lights, or a perspective camera — staying inside the project's existing "2D-in-camera-space, procedural, fullscreen-quad, WebGL2-gated, prerendered-PNG-fallback" envelope — and (b) the ones that quietly already ship in three.js's addons folder (the official TSL Raymarching util, MarchingCubes, the WebGL2 Data3DTexture volume path) that almost nobody reaches for because the tutorials all hand-roll GLSL. Hard reality to flag up front: most of the genuinely NEW 2026 raymarch surface (TSL RaymarchingBox, VolumeNodeMaterial) is WebGPURenderer-only, which is a renderer swap chaipalaka has NOT made (it's @react-three/fiber on WebGL2) — so those are tagged as opt-in heavy-route / second-renderer ideas, not drop-ins, and the WebGL2-native picks are called out as the ones that fit today's stack with zero renderer change.
- **RaymarchingBox — three/addons/tsl/utils/Raymarching.js (TSL)** — An OFFICIAL three.js addon (lives in the examples/jsm tsl/utils folder, not core) that wraps the boilerplate of a fixed-step raymarch loop inside a bounding box. You call RaymarchingBox(steps, ({ positionRay }) => { ... }) inside a TSL Fn and write only the per-step body — accumulate density, sample a 3D field, early-out — and it generates the WGSL/GLSL loop, ray setup, and box intersection for you. It is the sanctioned, maintained replacement for the hand-rolled 'for(int i=0;i<STEPS;i++)' fragment shader every raymarch tutorial copy-pastes.
  - rare: Almost nobody knows it exists. Every raymarch article from 2019–2026 still teaches you to write the marching loop by hand in a ShaderMaterial fragment shader; the fact that three.js now SHIPS a tested loop primitive in its addons tree is buried in the docs (module-Raymarching) with essentially zero tutorial coverage. People reach for danielesteban/three-raymarcher or raw GLSL instead of the in-tree util.
  - constraints: TSL utility — practically WebGPURenderer-bound today (TSL compiles to WGSL on WebGPU, falls back to GLSL, but the volume/Node material path is reliably exercised only on WebGPURenderer in r184; WebGL Node-material support was still being landed). chaipalaka runs @react-three/fiber on WebGLRenderer/WebGL2, so this is an OPT-IN heavy route requiring a second WebGPURenderer canvas behind the existing WebGL2/WebGPU detect, NOT a drop-in. SSR/no-JS: same envelope as the existing 9 scenes — lazy-chunk it per route, gate behind a WebGPU detect, ship the prerendered PNG + no-JS gradient fallback; the bundle-split rule means it must never import into a plain reading route. (verify the exact callback signature {positionRay} against the pinned r184 build before relying on it — the addon API is young and has changed shape.)
  - site seed: A 10th, explicitly-experimental background scene — '/lab/sdf' — where the fullscreen quad raymarches a small set of SDF spheres whose CENTERS are fed from the matter.js Card body positions the physics loop already computes each tick (pass them as a uniform array). Cards would cast a soft volumetric 'aura' / metaball field BEHIND the DOM, so the GPU background and the CPU foreground finally talk to each other instead of being two unrelated RAF loops. Opt-in, WebGPU-gated, never on a reading route.
- **WebGL2 Data3DTexture + bounding-box backface raymarch (the webgl2_volume_* path)** — The WebGL2-NATIVE volumetric technique three.js has shipped for years and that fits chaipalaka's CURRENT renderer with zero WebGPU dependency: upload a 3D field (e.g. tiled 3D Perlin/worley noise, or a baked density grid) into a Data3DTexture, rasterize the BACKFACES of a unit cube to launch fragment-shader work only where the volume is, and step a ray through the texture inside that fragment shader accumulating density. This is the engine behind the classic webgl2_volume_cloud / webgl2_volume_perlin examples.
  - rare: Underused because (a) everyone now assumes 'volumetrics = WebGPU' and skips the perfectly-good WebGL2 path, and (b) Data3DTexture is unfamiliar — most devs only ever touch 2D DataTexture, and the backface-bounding-box trick (rasterize backfaces, not a fullscreen quad, to bound the march) is a non-obvious optimization that tutorials gloss over. It is the highest-fit volumetric option for this site precisely because it needs no renderer swap.
  - constraints: Requires WebGL2 (3D textures are WebGL2-only) — chaipalaka already gates on WebGL2/WebGL, so this slots into the existing detect with no new capability gate. Perf: 3D texture sampling × march steps is fill-rate heavy; keep the texture small (64^3–128^3), cap steps, and render at reduced resolution. Strictly procedural, no lights/no models/no perspective-camera needed (an ortho/screen-space framing works), so it stays inside the project's stated background envelope. SSR/no-JS: lazy-chunk per route + prerendered PNG + no-JS gradient, same as the other 9 scenes; keep it out of reading-route bundles. (verify the exact current example filename — webgl2_volume_perlin vs webgl2_volume_cloud — against the r184 examples index.)
  - site seed: A drifting volumetric-fog background for a single 'atmosphere-heavy' essay route: a thin animated 3D-noise cloud layer behind the content box, density modulated by scroll position (denser as you read deeper). Because the content box's four edges are already registered as static physics walls, the fog could be made to 'pool' against the box silhouette by darkening the march where the ray's screen-space position falls inside the box rect — cheap parallax between prose and atmosphere, no WebGPU.
- **Smooth-minimum (polynomial smin) SDF blending — the metaball operator** — The single SDF operator that makes raymarching look ALIVE rather than like a CSG demo: instead of min(a,b) to union two distance fields (which gives a hard crease), smin(a,b,k) blends them with a smooth, controllable falloff so two approaching spheres gloop together like mercury/lava-lamp metaballs. Paired with the analytic SDF primitives (sdSphere, sdRoundBox, sdCapsule) and domain ops (twist, repeat, displacement), it is the core vocabulary of expressive SDF scenes.
  - rare: It's 'known' in the shader-demo subculture (Inigo Quilez) but almost never appears in three.js-specific work — three.js devs default to MarchingCubes for metaballs (geometry-based, coarse) and never realize the fragment-shader smin gives infinitely smooth blends at no triangle cost. It's a four-line GLSL function with outsized aesthetic payoff that hides in plain sight.
  - constraints: Pure shader math — runs anywhere a fragment shader does, including chaipalaka's existing WebGL2 ShaderMaterial scenes; NO WebGPU, NO new addon, NO dependency. Cost scales with primitive count × march steps (each step evaluates every smin term), so keep the primitive set small (≤~12). SSR/no-JS: it's just a shader inside an already-gated scene, so it inherits whatever fallback that scene ships. Footgun to respect: it must stay on a canvas background route — never let SDF GLSL leak into a reading-route bundle (the project's strict bundle-split rule).
  - site seed: This is the operator that makes the Card-aura idea actually beautiful: feed each matter.js Card body's center as an sdSphere, smin them together with k tuned so nearby Cards visibly MERGE into a single blob and split apart as the physics pulls them — a literal lava-lamp readout of the foreground physics state, rendered behind the DOM. The Tethers (rope = pull-only capsule between two anchors) become sdCapsule segments, so a strung Card's tether shows up as a thinning liquid bridge to its ceiling. Works on the current WebGL2 renderer.
- **MarchingCubes — three/addons/objects/MarchingCubes.js** — The GEOMETRY-side counterpart to fullscreen raymarching: a real Object3D that voxelizes a scalar field on the CPU/GPU and triangulates an isosurface every frame via marching cubes, giving you actual mesh metaballs you can light, shadow, and intersect with other scene geometry. You addBall(x,y,z,strength,subtract) / addPlane() and it rebuilds the surface. Ported from greggman's classic blob demo.
  - rare: Underused on the modern web because it predates the raymarching hype and feels 'old', and because people assume metaballs must be a shader. But it occupies a niche the fullscreen raymarchers can't: the blob is GENUINE GEOMETRY, so it participates in depth/occlusion, casts shadows, and composites with normal meshes — and it works on plain WebGLRenderer with no WebGPU and no fullscreen-quad fill-rate cost.
  - constraints: CPU/JS field evaluation cost scales with resolution^3 — keep the grid coarse (~28–48) or it tanks the frame. It DOES introduce real 3D geometry + needs a light to look like anything, which pushes against chaipalaka's stated 'NO models / NO lights / NO perspective camera' background convention — so this is the one pick that, if used, knowingly OPTS OUT of that convention for a deliberately 3D moment, not a fullscreen-quad scene. WebGL only, no WebGPU. SSR/no-JS: lazy-chunk + PNG fallback like the others; must not import into reading routes.
  - site seed: A deliberately-3D 'about/lab' landing flourish (not a reading route) where a slowly-rotating metaball blob made of MarchingCubes balls reads the same Card positions — but here as actual lit geometry the cursor can orbit. Use it only where a single perspective/lit moment is the point and the no-lights convention is intentionally suspended; everywhere else prefer the fullscreen smin raymarch above (no geometry, no lights).
- **three-good-godrays — screen-space raymarched volumetric light (pmndrs postprocessing EffectPass)** — A screen-space, raymarched god-rays / volumetric-light EffectPass built on the pmndrs postprocessing library: it marches each pixel's ray back toward a light, samples the shadow map at each step to test occlusion, and accumulates in-scatter — producing true volumetric light shafts that respect scene geometry, composited as a post-process over the rendered frame rather than a standalone fullscreen demo.
  - rare: The built-in three.js webgl_postprocessing_godrays example is the radial-blur fake (occlusion-masked screen blur), which everyone copies and which only works for a light on-screen. The genuinely raymarched, shadow-map-sampling version (three-good-godrays) is comparatively obscure and is the one that actually looks volumetric — but it's a third-party addon most people never find, and it plugs into the pmndrs postprocessing EffectComposer that R3F sites often already have but rarely use for raymarched effects.
  - constraints: Needs the pmndrs postprocessing library (a declared dependency — chaipalaka does NOT list it today, so adopting it is a new top-level dep + an EffectComposer in front of the renderer) AND a shadow-casting light + shadow map for the march to sample, which collides with the site's 'no lights' background convention. WebGL (no WebGPU required). Perf: per-pixel march × shadow sample is expensive; render at reduced resolution / step count. SSR/no-JS: same lazy-chunk + PNG + gradient fallback discipline; never on a reading route. (verify three-good-godrays' peer-dep range against chaipalaka's pinned three r0.184 before adding — addon/three version skew is the usual breakage.)
  - site seed: Reserve this for ONE opt-in cinematic route (e.g. a project case-study cover) where a single low, raked light source throws volumetric shafts past floating Cards — the Cards' DOM-mirrored physics bodies become the occluders. Heavy, deliberate, never default; lives behind the WebGL gate with a static PNG hero for no-JS and reduced-motion.
- **troika-three-text — on-the-fly SDF/MSDF glyph atlas text** — The de-facto high-quality text renderer for three.js: it parses font files (.ttf/.otf/.woff) with Typr, generates a signed-distance-field atlas for each glyph ON DEMAND (GPU-accelerated when WebGL is available, web-worker JS fallback otherwise), assembles a geometry, and PATCHES any three.js material's shader to sample the SDF — giving crisp, scalable, antialiased text at any zoom with proper kerning, ligatures, and RTL/bidi. It is screen-space distance fields applied to type.
  - rare: Within the raymarch/SDF VEIN it's the most overlooked instance of the technique: people think 'SDF' and reach for raymarched blobs, forgetting that the most practical, shippable distance-field tool in three.js is a TEXT renderer. Devs default to DOM text or canvas-texture text (blurry on zoom) and never realize troika gives them resolution-independent, shader-deformable type backed by real SDF atlases.
  - constraints: External dependency (troika-three-text — NOT currently in chaipalaka's manifest, so a new declared top-level dep). Renders in WebGL; the SDF generation prefers GPU but falls back to a worker, so it works without WebGPU. SSR/no-JS: it's canvas/WebGL text, so it produces NOTHING for the no-JS path and must NEVER replace the prose in a content route — it's a decorative/canvas-layer tool only, with the real readable text staying as prerendered DOM. Worker + font-parse adds startup cost; not for body copy. NOTE chaipalaka already uses @chenglou/pretext for canvas TEXT MEASUREMENT — troika overlaps in spirit but solves rendering, not prediction; don't conflate them.
  - site seed: Decorative, canvas-only display type for the experimental landing/lab routes: an oversized site wordmark rendered as troika SDF text whose glyphs the cursor-repel lattice (an existing background scene) can push around, or whose SDF edge a shader can make 'bleed' into the volumetric fog. Because it's true SDF, it stays razor-sharp through any scale/parallax. Keep it strictly ornamental — the gwern-prose reading routes keep their plain prerendered DOM text.
- **Analytic raymarched soft shadows + AO via the distance field itself** — Two 'free' lighting tricks that fall out of having an SDF and that most people never exploit: (1) SOFT SHADOWS by marching a single ray toward the light and tracking the minimum (distance-to-surface / distance-traveled) ratio along it — one extra march yields penumbra-correct soft shadows with a tunable softness, no shadow map; (2) AMBIENT OCCLUSION by sampling the field at a few short steps along the surface normal and comparing expected vs actual distance — cheap contact darkening. Both come essentially for free once a smin SDF scene exists.
  - rare: These are the 'second half' of an SDF scene that tutorials almost always omit — they teach you to march to a hit and slap on flat color, then stop. The result is the flat, plasticky SDF look everyone's seen. The analytic-soft-shadow and SDF-AO tricks are what separate a striking raymarch from a default one, and they're nearly unknown outside the demoscene/Quilez lineage; in three.js-land they're vanishingly rare.
  - constraints: Pure shader math on top of an existing SDF march — NO dependency, NO WebGPU, runs in chaipalaka's current WebGL2 ShaderMaterial. Cost: soft shadows add one secondary march per pixel (~2x the marching work); AO adds a few taps — both controllable. Only meaningful if you've ALREADY committed to an SDF scene (it's an enhancement to features 1–3, not standalone). SSR/no-JS: inherits the host scene's gate and PNG/gradient fallback. Keep it on background/lab routes, never in a reading-route bundle.
  - site seed: Apply directly to the Card-aura SDF background (features 1+3): give the metaball blobs analytic soft shadows from one fixed virtual light and SDF-AO in the creases where two Cards gloop together — so the moment two Cards collide in the matter.js sim, the GPU shows a soft contact-shadow darkening at the merge seam. It makes the physics-driven blob read as a real, settling liquid mass instead of a flat union, at the cost of one extra march. No new deps, current renderer.

### Geometry techniques — three.js ~r0.184 (2026). Scouting lesser-known geometry-side capabilities (not the shader/material vein). The site's current three.js usage is exclusively 2D-in-camera-space background quads/point clouds with NO real geometry, NO lights, NO perspective camera — so EVERY item here is, by construction, a departure from current usage. I therefore biased toward two flavors that fit anyway: (1) techniques that compute ON geometry CPU-side to feed the existing DOM/matter.js foreground (e.g. BVH spatial queries, SDF fields) WITHOUT adding a lit 3D scene, and (2) genuinely opt-in spectacle routes the owner has blessed as "anything goes". Hard-flagged: all of these are WebGL/canvas code and MUST stay lazy-chunked out of plain reading routes (bundle-split constraint), and none can run during SSR/no-JS — they need the existing prerendered-PNG + gradient fallback pattern. Three.js/react/vite pins are respected: every feature below ships in r0.184 core or is a standalone addon/npm package, none requires a three.js or React bump.
- **MeshBVH from three-mesh-bvh — closestPointToPoint / shapecast spatial queries (used HEADLESS, no render)** — three-mesh-bvh (gkjohnson, v0.9.x, the de-facto standard addon — three.js even shipped an official BatchedMesh+BVH example in r184) builds a bounding-volume hierarchy over any BufferGeometry. Beyond fast raycasting, its real power is the proximity API: closestPointToPoint(point, target) returns the nearest surface point + distance in sub-ms, and shapecast(callbacks) walks the tree against an arbitrary shape (box, sphere, capsule, another geometry) for collision/containment. You can build and query a BVH with NO renderer, NO scene, NO canvas — it's pure geometry math.
  - rare: 99% of tutorials use it only as a drop-in raycast accelerator (acceleratedRaycast). The proximity/shapecast half — querying 'where is the nearest edge of this shape to this point' as a standalone CPU computation decoupled from rendering — is almost never showcased, yet it's the most reusable part.
  - constraints: Pure JS/CPU, runs anywhere including a Web Worker — but the geometry it queries must exist in memory, so on a no-JS/SSR route it simply doesn't run (acceptable: it's an enhancement layer, not content). Build cost is O(n log n) once; queries are cheap. Undeclared top-level dep — must be added to package.json. Bundle ~tens of KB, so it must be lazy-chunked behind the same WebGL-detect gate as the existing scenes even though it needs no GPU.
  - site seed: Use it as the geometry brain for the Cards/Tethers foreground WITHOUT touching the GPU. Build a tiny BVH over the content-box outline (or any complex prose-column silhouette) and per-frame call closestPointToPoint(cardCenter) to drive tether anchor points or 'magnetic' card snapping to the nearest prose edge — replacing the four flat static walls with true nearest-surface attraction. Pure CPU, feeds matter.js exactly like today's tick. Lets a Card 'know' the shape of the text it's hanging off, not just a bounding rect.
- **MeshBVH.generateSDF / closestPointToGeometry — signed-distance field baking** — The same three-mesh-bvh library can bake a geometry into a signed-distance field: sample a 3D (or, for our purposes, 2D-slice) grid, call closestPointToPoint at each cell, and you get a distance texture you can feed to ANY shader as a uniform. The repo ships a generateSDF worker example. The output is just a Float/RG texture — it does not require the SDF's source mesh to ever be rendered.
  - rare: SDF generation is usually associated with offline tools (Blender, msdfgen) or hand-written GLSL distance functions. That three-mesh-bvh can bake an SDF from arbitrary geometry at load time, in-browser, in a worker, is a genuinely under-used capability — most devs don't realize the BVH proximity query IS an SDF generator.
  - constraints: Baking is the expensive step (do it once, off the main thread via the provided worker); sampling the resulting texture in a shader is cheap. The SDF texture is a GPU resource, so this is WebGL-only and lazy-chunked — but baking itself is CPU and could even be precomputed at build time and shipped as a PNG/EXR, dodging the runtime cost AND fitting the existing 'prerendered asset' pattern. Memory grows with grid resolution. three-mesh-bvh dep applies.
  - site seed: Bake an SDF of the actual page headline glyphs (you already measure glyphs with @chenglou/pretext) and feed it as a uniform into the existing flow-noise / reaction-diffusion background scene, so the ambient field warps AROUND the title text — the background 'feels' the foreground typography. Bake at build time, ship the SDF as one of the prerendered assets you already ship; zero runtime cost, no new scene, stays within the 2D-quad background idiom.
- **MarchingCubes addon (three/addons/objects/MarchingCubes.js) as a 2D metaball field** — The core MarchingCubes addon polygonalizes an implicit scalar field (sum of radial 'ball' contributions) into a smooth mesh in real time — the classic metaball/blob effect. addBall(x,y,z,strength,subtract) accumulates the field; you can also addPlaneX/Y/Z for walls. It's a CPU iso-surface extractor that emits geometry each frame.
  - rare: Everyone has SEEN the demo; almost nobody ships it, because in 3D it reads as a dated 'lava lamp'. The under-appreciated move in 2026 is constraining it to a thin slab / near-orthographic view so it reads as a 2D gooey-merge effect — which is exactly the camera regime this site already uses, and which most three.js metaball demos never try.
  - constraints: Pure CPU surface extraction every frame — cost scales with resolution^3, so keep the grid small (a flat slab keeps one axis at ~2-4 cells). WebGL render of the resulting mesh; lazy-chunk it; no-JS gets the static fallback. Needs a material — but a flat unlit/MeshBasic keeps it within the site's no-lights constraint. r184 core addon, no version risk.
  - site seed: An opt-in 'goo' background variant where each PEEK card spawns a metaball at its screen position; as you keep/cluster cards (the Ladder), their fields merge into one organic blob behind the prose — a literal visual of 'these links are becoming one collected thing'. Drive ball positions straight from the existing matter.js card bodies; orthographic slab so it reads 2D and matches the other background scenes.
- **three-bvh-csg (Brush + Evaluator, SUBTRACTION / INTERSECTION) — real-time boolean geometry** — three-bvh-csg (gkjohnson, v0.0.18) does fast, dynamic constructive solid geometry on top of three-mesh-bvh: wrap meshes as Brush objects, then evaluator.evaluate(a, b, SUBTRACTION) returns a new mesh that is a minus b — fast enough to recompute as the operands move. It's the modern, performant replacement for the old, abandoned THREE-CSGMesh.
  - rare: CSG in the browser was historically slow and janky, so the technique got written off; few realize 2026-era BVH-accelerated CSG can run interactively per-frame. It remains an exotic addon almost no production site ships.
  - constraints: Re-evaluating CSG every frame is the heavy path — fine for a handful of low-poly operands, not for dense meshes. WebGL-rendered output, lazy-chunked, no-JS fallback. Two undeclared deps (three-bvh-csg + its three-mesh-bvh peer). Genuinely a heavy/opt-in-route technique, not for a reading page. (verify) pin three-bvh-csg against the installed three r0.184 — it tracks three closely but is pre-1.0, so confirm the exact version resolves cleanly before relying on it.
  - site seed: An opt-in 'about' / playground route where the ENTER navigation hole is literally carved: a solid slab is SUBTRACTED by the expanding clicked-card volume during the hero-morph, so the destination content box appears to be punched through a wall rather than cross-faded. Strictly an experimental route the owner has blessed; the default hero morph (View Transitions) stays untouched, this is the spectacle alternative for one or two routes.
- **Line2 / LineGeometry / LineMaterial fat lines — WITH the new lines/webgpu/Line2.js variant** — Line2 (three/addons/lines/) renders screen-space-thickness polylines via instanced quads, with real px lineWidth, dashes, per-vertex colors, and rounded caps — things native THREE.Line (locked to 1px on most GPUs) can't do. As of 2026 there are TWO importable variants: the classic WebGL Line2 and a new lines/webgpu/Line2.js for WebGPURenderer, plus webgpu_lines_fat / _raycasting examples.
  - rare: Devs reach for the buggy native Line, hit the 1px wall, then drop to a 2D <canvas> or SVG — bypassing the fact that three.js has shipped a proper fat-line solution for years. The brand-new WebGPU twin is barely known. Underused because the import path (three separate classes: Line2 + LineGeometry + LineMaterial) is non-obvious.
  - constraints: WebGL2 (or the WebGPU variant on capable browsers — but WebGPU is NOT universal in 2026, so the WebGL Line2 stays the safe default). Lazy-chunk; no-JS gets nothing (it's decorative). Raycasting fat lines needs the dedicated raycast path. Resolution uniform must track canvas size or widths break on resize.
  - site seed: Render the Tethers as fat lines in a thin transparent overlay canvas instead of (or behind) the DOM rope: variable width that thickens with rope tension, dashes that animate along a taut tether, color that shifts slack→taut — far richer than a CSS/SVG line and impossible at 1px. Geometry is just the two matter.js anchor points per frame; sits in a 2D ortho overlay, fully consistent with the existing background-canvas regime, and degrades to the current DOM rope if WebGL is absent.
- **DecalGeometry (three/addons/geometries/DecalGeometry.js) — projected surface geometry** — DecalGeometry(mesh, position, orientation, size) generates a NEW geometry that is the clipped projection of a box onto a target mesh's surface — the standard way to 'paste' a texture (graffiti, bullet hole, label) that conforms to arbitrary curvature. It clips the target's triangles against the projector box and re-UVs them.
  - rare: It's a niche addon overshadowed by texture-atlas decaling and screen-space techniques; most three.js users never touch it. The under-appreciated insight is that it's a pure geometry generator — you get a mesh you can do anything with, including measure or animate, not just texture.
  - constraints: Needs a target mesh with usable normals/UVs; distorts around sharp corners (documented limitation). Each decal is its own draw call / geometry, so hundreds get expensive — pool/merge them. WebGL, lazy-chunked, no-JS none. r184 core addon, stable.
  - site seed: On an opt-in route that DOES have a real surface (e.g. a stylized 3D 'desk' or 'wall' object the cards live on), stamp each KEEP/pinned link as a decal that wraps the surface — the act of keeping a link leaves a physical projected mark conforming to the geometry, reinforcing the 'collect into the world' metaphor of the Ladder. Lower priority than the BVH/SDF items because it presupposes introducing real lit-ish geometry the site otherwise avoids.
- **ParametricGeometry / LatheGeometry / ExtrudeGeometry with custom UVGenerator + extrude bevel/steps** — The procedural geometry constructors: ParametricGeometry (moved OUT of core into three/addons/geometries/ in modern releases — confirmed an addon in 2026) builds a surface from a u,v→(x,y,z) function; LatheGeometry revolves a 2D profile; ExtrudeGeometry pushes a THREE.Shape along a path with bevels, multiple steps, and a UVGenerator hook. The deep, rarely-used parts are the extrude bevelSegments/steps/extrudePath and supplying your OWN UVGenerator.
  - rare: People treat these as toys for a single torus-knot demo and never explore the parametric-function or custom-UV depth — and many don't even know ParametricGeometry is no longer in core (a silent import break if you assume otherwise). Genuinely under-explored as a way to generate site-specific procedural forms from data.
  - constraints: All CPU geometry generation, cheap if built once and not regenerated per frame. ParametricGeometry MUST be imported from three/addons now — assuming core breaks the build (relevant to the bundle-split/pin discipline). WebGL render; lazy-chunk; no-JS none. No version risk if import paths are correct.
  - site seed: Drive an ExtrudeGeometry from real site data — e.g. extrude the Shape of your reading-activity sparkline (or a glyph outline measured via pretext) along a curved extrudePath to make a per-page procedural 'ribbon' masthead object, with a custom UVGenerator mapping the ambient background field across it. It's a content-derived, deterministic form (good for the prerendered-PNG fallback: render the same geometry server-ish at build time to a static image), keeping it honest with the SSR/no-JS requirement.

### Reflection, refraction, portals & cameras
- **Camera.setViewOffset (off-axis / sub-rect projection) — PerspectiveCamera & OrthographicCamera** — A built-in camera method (on both Perspective and Orthographic cameras) that re-derives the projection matrix to render an arbitrary sub-rectangle of a larger 'virtual' frame: setViewOffset(fullWidth, fullHeight, offsetX, offsetY, width, height). It is the engine's general off-axis / asymmetric-frustum primitive. Canonical uses: tiled hi-res rendering (render a 4000x4000 poster as a grid of tiles), GPU picking (offset to a 1x1 rect under the cursor into a 1x1 render target, then readRenderTargetPixels), and — the underused one — a 'window into a world' where the frustum is sheared so the camera looks *through* a fixed DOM rectangle (monitor/portal/peephole parallax) rather than at a centered target. clearViewOffset() restores the symmetric frustum.
  - rare: 99% of tutorials only ever touch it via the official GPU-picking example and never explain that the SAME call gives asymmetric/off-axis frustums for free — no custom projection-matrix math. The 'shear the frustum so a fixed on-screen rectangle becomes the window' trick (the basis of fish-tank VR and convincing 2.5D parallax) is folklore that almost nobody reaches for, because people assume you must hand-roll makePerspective() with custom left/right/top/bottom.
  - constraints: Pure CPU matrix recompute, effectively free; works on WebGLRenderer and WebGPURenderer alike. No SSR/no-JS implication — it is a runtime camera tweak, irrelevant to prerender. Known r184 gotcha (verify against your scene): the 1x1-pixel + setViewOffset GPU-picking path mis-samples THREE.Points (three.js issue #31395) — fine for mesh/quad picking, flaky for point clouds. CSS3DRenderer does NOT honor setViewOffset (issue #21723), so a sheared frustum won't carry to any CSS3D layer.
  - site seed: The background scenes are full-screen quads viewed by a camera that today does nothing interesting. Wire pointer position into a small setViewOffset shear so the procedural noise/lattice/starfield gets a subtle off-axis parallax — the flat quad gains apparent depth and 'looks through' the content box like a window, with zero new geometry. Separately, this is the cleanest way to add GPU picking over the background quad if you ever want a hovered point in the boids/voronoi field to drive a Card spawn.
- **renderer.setScissor / setViewport / setScissorTest — multi-region single-canvas rendering** — Low-level WebGLRenderer/WebGPURenderer calls that confine drawing to a rectangular region of the single canvas. Pair setViewport(x,y,w,h) (where it draws) with setScissor(x,y,w,h)+setScissorTest(true) (where it is allowed to clear/write) to render N independent camera views into N rectangles of ONE canvas in one frame — split-screen, picture-in-picture insets, a strip of 'thumbnail' cameras, or a magnifier loupe that re-renders the same scene zoomed into a small box. Each region can have its own camera and even its own scene.
  - rare: Everyone reaches for a second <canvas> / second WebGLRenderer (or N R3F <Canvas> elements) when they want multiple views, paying full per-context overhead and a second RAF. The single-canvas scissor pattern is in the official examples (webgl_multiple_views) but rarely used in production because it forces you out of the comfortable 'one camera, one full-screen quad' mental model. It is the cheapest way to get many viewports.
  - constraints: One GL/GPU context, one RAF — far cheaper than N renderers. Coordinates are bottom-left origin (y flipped vs CSS) and in DEVICE pixels, so you must multiply by devicePixelRatio — the classic bug source. Known issue: scissor/viewport interacts badly with EffectComposer/post-passes (three.js #5979), so combine it with full-screen post-processing carefully. SSR/no-JS irrelevant (runtime only). Works on both renderers.
  - site seed: A 'peek' Card today is a DOM preview. For a richer opt-in peek on a heavy route, render a small live inset of the *destination's* background scene into a scissored rectangle that sits exactly where the peek Card's matter.js body is — the preview literally shows the world you'd enter, in the same single background canvas, no second context. Or a loupe: a small scissored viewport that re-renders the reaction-diffusion field magnified under the cursor.
- **CSS3DRenderer (three/addons/renderers/CSS3DRenderer.js) with CSS3DObject / CSS3DSprite** — An addon renderer that lays out real, live, interactive DOM elements in a 3D scene graph by emitting CSS3 matrix3d() transforms — no canvas, no WebGL. Your <div> stays selectable, clickable, accessible, and crisp at any zoom (it is vector DOM, not a rasterized texture), but is positioned/rotated/perspective-projected by a THREE.Camera. CSS3DSprite keeps the element always facing the camera (billboard).
  - rare: Sits in an awkward 'neither fish nor fowl' gap: 3D devs dismiss it because it can't share the WebGL depth buffer or materials, and DOM devs don't know a three.js camera can drive their divs. So it is wildly underused for exactly the case it nails — keeping text/UI as accessible DOM while giving it real perspective and a shared camera with a WebGL background. This is a near-perfect fit for a site whose foreground is *deliberately* DOM-not-GPU.
  - constraints: No three.js materials/geometry/lights, and it cannot occlude or be occluded by WebGL content via a shared depth buffer (you fake interleaving by carefully ordering a transparent WebGL canvas behind/in-front, or by matching cameras). 'Only supports 100% browser/display zoom' per the docs — non-100% OS zoom skews layout. SSR/no-JS: the renderer is JS-only, so wrap it as progressive enhancement — the divs must render as normal flow DOM with no JS (they already are real DOM), and the 3D transform is layered on after hydration; this keeps the no-JS content-route fallback intact. Strict-bundle-split: CSS3DRenderer is tiny and NOT WebGL, so it is safe to load on a reading route without dragging the 3D/canvas chunk in — but verify it's chunked separately from the R3F background bundle. Camera setViewOffset is NOT respected (#21723).
  - site seed: Cards are already absolutely-positioned divs driven by matter.js. Add an OPT-IN '3D ladder' mode where the same Card divs are handed to CSS3DRenderer and given real perspective z-depth: a KEEP-pinned card sits slightly forward of the content box, PEEK cards recede, ENTER tilts the whole stack toward you — all while staying live, accessible DOM with selectable gwern-prose text. The matter.js 2D positions become the x/y; CSS3D adds the z. No raster, no text blur, no-JS still gets flat divs.
- **CubeCamera + WebGLCubeRenderTarget for real-time per-frame environment capture** — A rig of six perspective cameras that renders the surrounding scene into a live cube render target every frame (cubeCamera.update(renderer, scene)), producing an environment map you can feed to any material's .envMap for dynamic reflections/refractions that update as the scene changes — not a baked static HDRI. Pair with a refractive material (or feed a Refractor) for live refraction.
  - rare: Most 'reflections' in the wild are a static loaded HDRI envMap that never updates — genuinely DYNAMIC cube capture (re-rendering the world 6x/frame so reflections track motion) is avoided for cost and is therefore rare and visually striking when present. Underused because people don't realize a CubeCamera can capture a *2D procedural* scene just as well as a 3D one.

- **Object3D.layers + Camera.layers (bitmask layer routing) and Raycaster.layers** — Every Object3D and Camera carries a 32-bit Layers bitmask (.enable/.disable/.set/.toggle). A camera only renders objects sharing at least one enabled layer bit; a Raycaster only hits objects on its layers. This is three.js's first-class mechanism for 'render this set of objects in pass A, that set in pass B' WITHOUT maintaining separate Scene graphs — the routing key for selective bloom, reflection masking (hide the mirror from its own reflection camera), and per-viewport object visibility in the scissor/multi-view setups above.
  - rare: Layers are quietly powerful but their 32-bit-bitmask API (enable vs set, the off-by-one of layer 0 being default-on) is confusing enough that people instead juggle .visible toggles or duplicate scenes — both more error-prone. Almost every multi-pass effect that 'should' use layers is hand-rolled with visibility flags. The selective-bloom and reflection-self-exclusion idioms are the canonical underused wins.
  - constraints: Zero runtime cost (it's a bitmask test in the cull loop). Only 32 layers. Layer 0 is enabled by default on everything — a frequent footgun when you .set() and accidentally remove an object from the default camera. Works identically on WebGL and WebGPU; raycaster honors them too. No SSR/no-JS dimension. Note CSS3DRenderer does not participate in WebGL layer culling (it has its own scene).
  - site seed: If you add the CubeCamera reflective Card (above) or any multi-view scissor inset, use layers to keep the reflective object out of its own capture and to route 'background-only' vs 'foreground-card-proxy' objects to the right pass cleanly — instead of toggling .visible on every frame. Also the natural enabler for a selective-bloom 'glow' on exactly one KEEP-pinned card's GPU proxy while leaving the rest of the background un-bloomed.
- **WebGLRenderTarget portal pattern — render Scene B to a texture, map it onto a quad/frame in Scene A (+ stencil-buffer portal alternative)** — The general render-to-texture portal: create a WebGLRenderTarget, renderer.setRenderTarget(rt); renderer.render(sceneB, cameraB); setRenderTarget(null), then use rt.texture as the map of a plane (the 'window'/'frame') in your main scene. A literal window into another world. With a camera in Scene B that tracks the viewer, you get a parallax-correct portal; with a DepthTexture attached you can even composite depth. The geometric alternative is the stencil-buffer portal: write a per-portal index (1..255) into the stencil at the aperture, then clip the inner scene to that stencil region — true edge clipping, no second render target.
  - rare: R3F users mostly reach for drei's <RenderTexture>/<MeshPortalMaterial> and never learn the raw setRenderTarget dance, so the technique is seen as a 'drei thing' rather than a 5-line core primitive. The depth-correct variant (attaching a DepthTexture, or shearing the portal camera via setViewOffset to match the frame) is genuinely rare, and hand-rolled stencil portals rarer still. It's the bridge that lets a flat framed rectangle feel like an opening — which fits a site built around 'a Card that expands into a destination.'
  - constraints: Render-target portal: one extra full scene render per portal per frame — keep targets small and few; the target must render before the main pass that samples it. Stencil portal: needs stencil enabled on the renderer, careful render-order (draw the aperture last, depth-tested, so nearer objects don't get punched through), ~255 portal cap; heavier to wire but no second target. SSR/no-JS: the portal frame should degrade to a static prerendered PNG (you already ship per-scene PNGs) so no-JS/non-WebGL shows a still 'postcard.' Must live in the canvas chunk, never the reading-route bundle. Both renderers support render targets; verify stencil specifics on WebGPU if you ever migrate.
  - site seed: Make ENTER literally a portal: the clicked Card's rectangle becomes a WebGLRenderTarget showing the destination route's background scene rendered live behind it, so the View-Transition hero-morph dissolves from 'card-as-DOM' into 'card-as-window-into-the-next-world' before the client nav completes. The portal frame == the morph-target element's view-transition-name region; fallback (no VT / no WebGL) is your existing plain client nav + prerendered PNG.
- **Reflector & Refractor addons (three/addons/objects/) — and ReflectorNode for the WebGPU/TSL path** — Reflector is a drop-in mirror Mesh: it owns an internal camera + render target and re-renders the scene from the mirror's reflected viewpoint into the surface, giving true planar reflections (real perspective, not a fake cube/HDRI). Refractor is its refraction twin for flat refractive surfaces (windows, water). Both predate and are cheaper-per-mirror than a CubeCamera for a FLAT surface. The WebGPU/TSL counterpart is reflector()/ReflectorNode, used with WebGPURenderer — renderer-agnostic TSL, but it requires the WebGPU renderer, NOT the WebGLRenderer your site runs today.
  - rare: Planar Reflector is overshadowed by envMap/HDRI reflections in every PBR tutorial, so people forget three.js ships a true-mirror addon that needs no environment asset. Refractor is even more obscure — most devs never discover it exists. And the WebGPU ReflectorNode is brand-new enough (post-WebGPU-maturity, ~2025) that almost no production sites use it yet.
  - constraints: Each Reflector/Refractor = one extra scene render per frame (its hidden camera); flat surfaces only (no curved mirrors — that's CubeCamera's job). Encoding/colorSpace must be set correctly or the mirror looks washed (the .encoding/.colorSpace fixes from three's own PRs). Big one for THIS site: Reflector/Refractor classes are WebGLRenderer-bound; ReflectorNode requires WebGPURenderer, and your three/toolchain are pinned by vite-react-ssg — adopting WebGPU is its own project, NOT a free switch (verify any TSL node API names against r184). SSR/no-JS: runtime canvas only, opt-in route, prerendered-PNG + gradient fallback as usual; keep in the canvas chunk.
  - site seed: The content box is a flat rectangle with registered physics walls — its bottom edge could host a Refractor or a floor-Reflector that mirrors the procedural background, so prose 'floats over water' on one spectacle route. Cheaper and crisper than CubeCamera because it's planar. Stay on the Reflector (WebGL) class for now; note ReflectorNode as the upgrade path IF/when a WebGPU migration becomes its own slice — don't pin the design to a renderer you haven't migrated to.
- **Browser HTML-in-Canvas API: context.drawElementImage() / element-to-canvas capture (experimental) feeding a CanvasTexture** — A new, browser-native (NOT three.js) Canvas2D API that rasterizes a LIVE, fully-rendered DOM element — real CSS, fonts, filters, the works — straight into a canvas at GPU speed, which you then wrap in a THREE.CanvasTexture and map onto geometry. It is the long-awaited 'correct' replacement for the html2canvas / SVG-foreignObject hacks that only ever supported a CSS subset and dropped fonts/SVG. Lets you take genuine, accessibility-authored DOM (your gwern prose, a Card) and use it as a real texture in the 3D scene.
  - rare: Brand new and behind a flag — barely anyone has wired it to three.js yet, and the whole 'DOM-to-texture' space was so painful (html2canvas's partial CSS, foreignObject's font/CORS failures) that most devs gave up and re-authored text in canvas. So a working DOM->texture pipeline is rare *and* about to get dramatically better.
  - constraints: EXPERIMENTAL — drawElementImage / HTML-in-Canvas is flag-gated and not broadly shipped as of 2026 (verify current browser support before relying on it; treat strictly as progressive enhancement). Legacy fallbacks each have hard limits: html2canvas supports only a CSS subset and no SVG; SVG-foreignObject drops cross-origin images, stylesheet-declared styles, and unloaded fonts. Re-rasterizing every frame is costly — capture on change, not per frame. SSR/no-JS: entirely a JS/runtime enhancement; the underlying element must remain real DOM for the no-JS fallback, with the texture path layered on after hydration. Must not leak the canvas chunk into reading routes.
  - site seed: When a Card morphs/enters, you currently can't put its live DOM *inside* a WebGL effect. Today: prototype on html2canvas knowing its CSS limits; design so the real DOM is always the source of truth and the texture is throwaway.

### Scroll-driven motion & transition tech
- **RenderTransitionPass (three/addons/postprocessing/RenderTransitionPass.js) — texture-threshold dissolve mode** — An official postprocessing addon that takes TWO full scene+camera pairs, renders each into its own HalfFloat WebGLRenderTarget, and cross-blends them in one fragment pass. Constructor is `new RenderTransitionPass(sceneA, cameraA, sceneB, cameraB)`. The under-used part is NOT the linear `setTransition(0..1)` crossfade everyone copies — it is `useTexture(true)` + `setTexture(tex)` + `setTextureThreshold(t)`, which turns the blend into a luminance-driven WIPE: the transition texture's brightness decides per-pixel which scene wins at a given threshold, so a noise/gradient/SDF map gives you ink-bleed, erosion, swipe, or shaped reveals instead of a flat fade.
  - rare: Tutorials universally demo the bare `setTransition` slider crossfade and stop there; the texture-threshold path (the actual creative lever) is buried in the example and rarely shown. People reach for the pmndrs/postprocessing library or hand-roll a ShaderPass and never discover three core ships a transition pass at all. Driving the threshold off a *measured* value (scroll, a card's settle energy) rather than a clock is essentially never done.
  - constraints: WebGL2 path is fine (HalfFloatType target needs EXT_color_buffer_float, ubiquitous in 2026). Cost = rendering two scenes + one composite pass, so it ~2x's GPU for the transition window only. Pure background concern: it must stay inside the lazy-chunked R3F canvas bundle and NEVER leak into a plain reading route (bundle-split constraint). Zero SSR/no-JS implication since it only animates the prerendered-PNG-backed background. No WebGPU needed; this is classic WebGLRenderer. (verify) confirmed present in r0.184 examples/jsm/postprocessing as of the search above.
  - site seed: chaipalaka's nav is already a DOM/CSS View-Transitions hero-morph with zero WebGL participation. Use RenderTransitionPass to give the BACKGROUND its own coordinated identity change during that same morph: sceneA = the current route's ambient scene, sceneB = the destination's, and feed `setTextureThreshold` from the SAME morph-target signal's progress so the background dissolves through a shaped noise map exactly as the card reflows into the content box. The foreground (DOM cards) stays on View Transitions; the background gets a matched WebGL dissolve — two layers, one gesture.
- **AfterimagePass (three/addons/postprocessing/AfterimagePass.js) — feedback-damped motion persistence** — A one-uniform feedback pass: it keeps last frame in a render target and blends `damp` (default 0.96) of it under the new frame, so anything that moves leaves an exponentially-decaying trail. It is a 3-line drop-in trail/echo effect that turns any moving point cloud or shader into something with temporal memory, without you managing your own ping-pong FBOs.
  - rare: Overshadowed by UnrealBloomPass in every 'glow' tutorial; almost nobody knows three ships a free frame-feedback pass. The real trick — animating `uniforms['damp'].value` per-frame off an external signal so persistence breathes with motion instead of sitting at a constant — is essentially absent from the ecosystem. Most 'trail' effects are hand-built GPGPU; this is the cheap, legible version.
  - constraints: Single extra full-screen pass + one persistent RGBA target = cheap, but it's a full-frame feedback so it tints/ghosts EVERYTHING in that composer, not selected objects. WebGL2 fine, no WebGPU. Stays inside the canvas chunk; no SSR/no-JS concern (background only). Footgun: at very high `damp` (>~0.99) trails never clear and the buffer smears permanently — clamp it. preserveDrawingBuffer NOT required (the persistence is the pass's own RT, not the canvas).
  - site seed: The boids (~5500 pts) and cursor-repel lattice scenes are the obvious hosts: drop an AfterimagePass and the flock leaves comet trails. Scroll-couple it — map `damp` to scroll velocity so a fast scroll smears the background into long streaks and a still page lets it crisp up. That gives the otherwise-passive ambient layer a reaction to the reader's pace, on the one signal (scroll velocity) chaipalaka can compute without WebGPU.
- **Cross-route WebGLRenderTarget persistence via a single hoisted renderer + readRenderTargetPixels / shared FBO** — Keep ONE WebGLRenderer (and its WebGLRenderTargets) alive above the router so it survives route changes, and render the outgoing route's final frame into an offscreen RenderTarget, then use that captured texture as the seed of the incoming route's intro shader. The persistence primitives are `renderer.setRenderTarget(rt)` / `renderer.readRenderTargetPixels()` and, in R3F, the `useFBO` hook — combined with the renderer/canvas NOT unmounting on navigation.
  - rare: Almost every SPA tears down its R3F canvas per route (or has one global scene and just swaps content), so the idea of 'capture the last frame of route A as a texture and hand it to route B' is rare outside bespoke award-site work. The enabling fact — that a render target is just a texture you can carry across an unmount if the renderer outlives the route — is under-appreciated; people assume the GL context dies with the page component.
  - constraints: Demands a renderer hoisted above react-router's route boundary, which fights chaipalaka's hard bundle-split rule: the canvas must stay out of reading-route bundles, so a persistent renderer would have to live in a route-group layout that only mounts on canvas-bearing routes, never globally. WebGL2, no WebGPU. SSR/no-JS: irrelevant to the captured texture (client-only), but the persistent-renderer layout must still prerender to the static PNG fallback on the server. - **Coupling WebGL with the View Transitions API via preserveDrawingBuffer + an explicit captured-frame texture (NOT the live ::view-transition-old snapshot)** — The honest pattern for making a <canvas> participate in a browser-native view transition.   - rare: The default-canvas-snapshots-blank gotcha is a known sharp edge that bites people once and is rarely written up cleanly. - **CatmullRomCurve3 + getPointAt (arc-length) with a Frenet/ahead-point look target, scroll-parameterized** — A spline camera rig done correctly. `CatmullRomCurve3` defines the path; the under-used method is `getPointAt(u)` (NOT `getPoint(t)`): getPointAt reparameterizes by ARC LENGTH using the precomputed length table, so equal scroll deltas move the camera equal *distances* even where control points bunch. Pair it with a second sample slightly ahead (`getPointAt(u + 0.02)`) as the lookAt target, or `computeFrenetFrames()` for full tangent/normal/binormal orientation, and bind `u` to scroll progress.
  - rare: Nearly everyone uses `getPoint(t)` and gets cameras that lurch — fast through sparse control points, crawling through dense ones — then blames easing.   - constraints: Pure CPU/JS math, near-free, no GPU at all — runs fine in chaipalaka's existing RAF without touching the renderer. - **AnimationMixer + NumberKeyframeTrack driving non-character, non-Object3D timelines (a generic property scheduler)** — three's animation system is usually sold as a glTF character-clip player, but AnimationMixer/AnimationClip/KeyframeTrack is really a general keyframe ENGINE with interpolation (linear/cubic/discrete), blending, weighting, crossfade, and time-scaling. A `NumberKeyframeTrack('.someUniform.value', times, values)` plus an AnimationObjectGroup lets you schedule arbitrary numeric properties — shader uniforms, a transition threshold, even a proxy object you read each frame — on a real timeline with AnimationAction controls (play/pause/crossFadeTo/setEffectiveTimeScale).

  - constraints: CPU-side, tiny cost; no GPU, no WebGPU. Property-path binding is stringly-typed and silently no-ops if the path is wrong — needs care. It's an imperative timeline, so it must be torn down on route unmount (mixer.stopAllAction) to avoid leaks. - **GPU geometry morph/dissolve via DataTexture-backed morph attributes (and the ShaderMaterial/RawShaderMaterial alternative)** — Built-in morph targets in r0.184 are uploaded as DataTextures and blended on the GPU via `morphTargetInfluences`, so a single mesh can interpolate between stored vertex states (e.g. scatter→assemble) by animating influences 0..1 — no per-vertex CPU work in steady state.   - rare: Morph targets are pigeonholed as facial-blendshape tech for rigged characters; using them (or the shader-attribute equivalent) for abstract point-cloud assembly/dissolve transitions is comparatively rare.   - constraints: Built-in morph has the upload cost above for large vertex counts and a finite influence-slot budget; the manual shader route avoids the upload cost but you give up the built-in machinery and write the mix yourself. WebGL2 fine, no WebGPU required. Pure background/canvas concern — must stay in the lazy canvas chunk. SSR/no-JS: the static PNG captures one frame of the morph; the no-JS fallback gradient shows neither endpoint, so pick a representative resting state. chaipalaka already ships custom ShaderMaterials (the flow-noise/reaction-diffusion scenes), so the two-attribute pattern is a natural extension of existing code.

One GPU mix, no new dependency, reuses scenes already on the route.

### Lighting & faux global illumination — cinematic light without a forward-lit 3D scene
- **ProgressiveLightMap / ProgressiveLightMapGPU (three/addons/misc/ProgressiveLightMap.js)** — An accumulation-buffer lightmap baker that lives entirely in-browser. You hand it a set of semi-static meshes (which need a second UV channel) plus lights, then call update(camera) every frame; it jitters the lights and progressively averages soft shadows + bounce-ish ambient occlusion into a lightmap texture that it blends onto the materials. After N frames it converges to a baked-looking, zero-cost-thereafter soft-GI surface. There is now a WebGPU sibling (ProgressiveLightMapGPU) that runs the same accumulation on the GPU compute/render path.
  - rare: Almost every web tutorial stops at a single hard DirectionalLight + basic shadow map and never touches lightmaps at all — baking is assumed to be a Blender-offline, glb-with-baked-textures workflow. Hardly anyone knows three ships a *runtime, in-browser* progressive baker as an addon. drei/r3f wraps it as <AccumulativeShadows>, so even people who use the technique often don't realise the vanilla addon exists or that a GPU variant landed.
  - constraints: WebGL build is fine on the broad install base; ProgressiveLightMapGPU needs WebGPU (no Safari-stable guarantee in 2026 — (verify) current Safari WebGPU status). Requires a 2nd UV set on every baked mesh — a real authoring tax. Cost is front-loaded: tens to a few hundred frames of jittered re-render to converge, so it briefly competes with your two existing RAF loops for the GPU; budget it as a one-time warmup, then it's static. Pure-render: nothing to prerender, so it's invisible to SSR/no-JS (the no-JS PNG fallback already covers that route). Don't run convergence on a reading route — it would violate the canvas-must-not-leak-into-reading-routes bundle rule unless lazy-chunked behind the WebGL gate like the other 9 scenes.
  - site seed: An opt-in 'studio' / about route where a few low-poly objects (or extruded versions of the Card glyphs) sit on a plane and accumulate genuinely soft, contact-hardening shadows over the first second of load — a quiet, expensive-looking still life that reads as 'baked' and motionless, the polar opposite of the procedural shader backgrounds. Because it converges then costs nothing, it coexists with the matter.js CPU loop without a sustained frame fight.
- **RectAreaLight + RectAreaLightUniformsLib (WebGL) / RectAreaLightTexturesLib (WebGPU) + RectAreaLightHelper** — A physically-plausible area light: light emitted from a rectangle (a window, a softbox, a glowing panel) using the Heitz/Hill LTC (Linearly Transformed Cosines) approximation. Unlike point/spot/directional lights it produces correct soft directional falloff and elongated specular reflections off the rectangle's shape. It only affects MeshStandardMaterial / MeshPhysicalMaterial, and you MUST call RectAreaLightUniformsLib.init() (WebGL) or load RectAreaLightTexturesLib (WebGPU) once to upload the LTC lookup tables before anything lights correctly.
  - rare: It's the one core three.js light that needs an explicit addon init call to work at all, so it silently does nothing for people who skip the uniforms-lib step — and they conclude it's broken and go back to SpotLight. It also casts no shadows, which scares people off. The payoff (real softbox specular streaks on a glossy surface) is exactly the 'cinematic product-shot' look the web almost never has.
  - constraints: No shadow casting (pair with contact/accumulative shadows for grounding). Standard/Physical materials only — won't touch the DOM Cards (those are CSS, not WebGL). LTC tables are a one-time uniform/texture upload, cheap per-frame. WebGL2 fine; for the WebGPU path use RectAreaLightTexturesLib. Render-only, so no SSR/no-JS implication beyond the usual gate. (verify) exact 2026 addon paths: three/addons/lights/RectAreaLightUniformsLib.js and three/addons/helpers/RectAreaLightHelper.js.
  - site seed: A glossy 'now-playing' or feature panel where a RectAreaLight standing in for the album art or a window throws a soft, shaped specular streak across a dark physical-material slab — gives a single hero object a luxe, lit-from-a-real-source feel that the flat procedural backgrounds and flat CSS Cards deliberately lack, marking it as 'the spectacle route'.
- **LightProbe + LightProbeGenerator.fromCubeRenderTarget / fromCubeTexture (three/addons/lights/LightProbeGenerator.js)** — A diffuse irradiance probe encoded as 3rd-order spherical harmonics (9 RGB coefficients) — functionally an irradiance environment map compressed to 27 numbers. LightProbeGenerator bakes one from any cube texture or live CubeCamera render target (fromCubeRenderTarget now returns a Promise), giving you image-based ambient lighting that wraps around objects with directional color (warm from one side, cool from another) for essentially free per-frame cost, since it's just an SH evaluation in the shader.
  - rare: SH light probes are textbook game-engine GI but almost unseen on the web; people reach for a full HDRI env map (scene.environment) and eat the texture memory + PMREM prefilter, not realising a 27-float probe gives 90% of the *diffuse* ambience at near-zero cost and can be sampled/baked from the scene itself. The capture-from-CubeCamera path (probe that reflects the actual page colors) is especially obscure.
  - constraints: Diffuse only — no glossy reflections (combine with a PMREM env map if you want specular). Baking via fromCubeRenderTarget does a GPU readPixels (there's a historical readPixels edge-case bug on some drivers — (verify) whether still open in 2026), so bake once, not per frame. The 9 SH coeffs are trivially serialisable, so you could even precompute them at build time and ship them as JSON — meaning the *lighting itself* can survive into a no-JS/SSR context as static data even though the render can't. Tiny bundle/perf footprint.
  - site seed: Precompute one SH probe per route from that route's procedural background's dominant palette (e.g. sample the reaction-diffusion or voronoi scene's colors), ship the 27 floats as static route data, and use it to tint any foreground 3D element so the lit object's ambient color *matches the live background* — a cheap, coherent through-line linking the GPU background and the lit foreground without rendering a full env map.
- **SSGINode (three/addons/tsl/display/SSGINode.js) — WebGPU/TSL screen-space global illumination + AO** — A newly-official post-processing node, written in TSL, that computes real-time screen-space global illumination AND ambient occlusion from the existing depth/normal/color buffers — one indirect-bounce of color bleeding plus contact darkening, no baking, no light setup. Quality/cost are dialled by sliceCount and stepCount (samples = sliceCount * stepCount * 2). It's the genuinely modern, 2025/2026-era addition to this vein.
  - rare: It's brand new and WebGPU-only, so it has almost no install base or tutorial coverage yet — most 'GI on the web' content is still SSAO or baked. Being a TSL node, it slots into the node-based post pipeline rather than the old EffectComposer pass chain people know, which further limits who's found it.
  - constraints: WebGPU ONLY — flatly excludes the WebGL/Safari-stable majority in 2026, so it's strictly an opt-in 'best browser' enhancement with a WebGL fallback path (e.g. GTAO/baked) required. Heavy: screen-space GI is one of the more expensive post effects; sliceCount*stepCount blows up fast on a laptop iGPU. Needs the WebGPURenderer, which your stack does NOT use today (the 9 scenes are R3F on WebGLRenderer) — adopting it means standing up a second WebGPU render path, a real project, not a drop-in. Render-only; SSR/no-JS unaffected but the route must double-gate (WebGL2 AND WebGPU).
  - site seed: Reserve for one flagship 'lab' route explicitly flagged as WebGPU-required: a small set of physical-material objects in a box getting soft color bleed off colored walls — the single most photoreal thing on the site, deliberately walled off behind a capability gate the way the playground framing invites, with the existing prerendered-PNG + WebGL scene as the graceful step-down.
- **GTAOPass (WebGL, three/addons/postprocessing/GTAOPass.js) / GTAONode (WebGPU TSL) — Ground Truth Ambient Occlusion** — The higher-fidelity successor to SSAOPass: Ground Truth Ambient Occlusion, a horizon-based AO that's far closer to a reference path-traced AO term than the blobby classic SSAO. In recent three.js it outright *replaced* HBAOPass, and there's a TSL GTAONode for the WebGPU/node pipeline. It darkens creases and contact points to fake the indirect-occlusion cue that sells depth.
  - rare: Tutorials overwhelmingly still teach SSAOPass (or no AO), and many people don't know HBAO was folded into GTAO or that GTAO exists as a stock addon. AO is the single cheapest 'this looks rendered, not flat' upgrade, yet it's routinely skipped on the web because the default-lit look has no occlusion cue at all.
  - constraints: More expensive than SSAOPass (extra samples) but still a normal full-screen pass — fine on a mid laptop at 1x. WebGL2 for GTAOPass; GTAONode needs WebGPU. Requires depth + normals, so it presumes an actual rendered 3D pass (not your flat 2D-in-camera-space quads) to bite on. Render-only; the prerendered PNG already bakes whatever AO was visible, so no SSR/no-JS change. Composes badly with some other passes (e.g. SSR) — order matters in the composer. (verify) current addon path naming in r0.184.
  - site seed: Whenever a route does have real geometry (the studio still-life above, or extruded Card glyphs), drop a single GTAOPass into its composer so every contact crease and stacked-object gap gets a soft grounding shadow — the one effect that makes the difference between 'WebGL toy' and 'this was lit', for a near-trivial cost, on the broadly-supported WebGL path.
- **Accumulated soft shadows via drei <AccumulativeShadows>/<RandomizedLight> — and the PCSS <SoftShadows> caveat** — drei's <AccumulativeShadows> is the r3f wrapper over the ProgressiveLightMap idea specialised to a ground plane: a Y-up shadow-catcher that jitters a <RandomizedLight> over many frames and averages the result into buttery, contact-hardening soft shadows with literally zero runtime cost once converged. Its sibling <SoftShadows> instead injects PCSS (Percentage-Closer Soft Shadows, the NVIDIA contact-hardening technique) directly into three's shadow shader chunk for *dynamic* soft shadows.
  - rare: Everyone uses hard shadow maps; the accumulate-then-freeze trick that gets you offline-quality softness in a live page is under-appreciated, and PCSS-on-the-web is rare because it's a shader-chunk patch rather than a component you can casually toggle. The contact-hardening cue (shadow sharp at the contact point, soft far away) is the exact thing that reads as 'real' and is almost universally absent on the web.
  - constraints: AccumulativeShadows is planar/ground-only and the object must be roughly static during accumulation — it re-bakes on movement, so it's for resting scenes, not animated ones (and your foreground is animated matter.js — so this is a separate, still, 3D layer, not the Cards). CRITICAL freshness flag: drei <SoftShadows>' PCSS broke on three r182 because three removed unpackRGBAToDepth — so a naive drei+latest-three combo errors at shader compile; pin compatible versions or use the patched drei (the pmndrs/drei #2583 fix). This is a live trap given your vite-react-ssg-pinned three. Render-only; no SSR/no-JS effect.
  - site seed: Use AccumulativeShadows as the grounding layer under the RectAreaLight studio object — the area light gives the shaped specular, the accumulated shadow gives the soft contact shadow it can't cast itself; together they're the full 'shot in a studio' look on one hero object, all WebGL, all converging-then-free, sitting peacefully alongside the CPU physics loop.
- **PMREMGenerator + scene.environment / scene.environmentIntensity / environmentRotation (IBL without an HDRI download)** — PMREMGenerator prefilters an environment into a roughness-stratified mipmap so MeshStandard/Physical materials get correct image-based diffuse AND glossy lighting from a single env source. The under-used trick is that the source need not be a multi-MB .hdr file: you can PMREM-prefilter a procedurally-generated scene (even a RoomEnvironment, a gradient, or one of your own GPU shaders rendered to a cube/equirect), and recent three exposes scene.environmentIntensity and scene.environmentRotation to dial and spin that ambient lighting cheaply.
  - rare: The default IBL tutorial is 'download this 8MB HDRI from polyhaven' — which is exactly the bundle-weight, network, and licensing baggage your strict-bundle, prerender-friendly site wants to avoid. Almost nobody PMREMs a *procedural* or synthetic environment, even though it gives coherent reflections for kilobytes and zero network. environmentIntensity/environmentRotation as first-class scene props are also newer than most tutorials.
  - constraints: PMREM prefilter is a one-time GPU cost at setup (cheap, do it once, dispose the generator). Affects Standard/Physical materials only — the DOM Cards are untouched. WebGL2 fine; works under WebGPU too. No network/bundle hit if the env is procedural — a real win for your no-HDRI, strict-split constraints. Render-only; SSR/no-JS unaffected (the prerendered PNG captures the lit result). (verify) that environmentRotation/environmentIntensity are the current property names in r0.184 (they were added across r150–r163-ish).
  - site seed: Render one of your existing background shaders (voronoi or flow-noise) into an equirect, PMREM-prefilter it once, and set it as scene.environment for a foreground physical object — the object then reflects and is ambient-lit by the very pattern animating behind it, for kilobytes and no HDRI download, and environmentRotation lets a slow spin couple the reflection subtly to scroll or the now-playing beat.

### Rare / underused core APIs & creative-coding tricks (clipping planes, custom depth materials, GPU picking, half-float feedback buffers, onBeforeRender/onBeforeCompile hooks, MRT, reversed/log depth, Shadertoy/reaction-diffusion plumbing). Verified against three.js r0.184 + @react-three/fiber 9.6.1 as pinned in web/package.json; the project already runs a manual WebGLRenderTarget ping-pong GPGPU pipeline (FloatType, raw ShaderMaterial, gl.setRenderTarget) in geometric-reaction-diffusion.tsx but uses NONE of the features below — so these are genuine leftovers here, not duplicates of the existing scenes.
- **WebGLRenderTarget({ count }) — multiple render targets (MRT), the merged successor to WebGLMultipleRenderTargets** — A single render target that writes N color attachments in ONE draw call. You pass count: N to the WebGLRenderTarget constructor; the fragment shader writes gl_FragData[0..N-1] (or layout(location=k) out vec4 in GLSL3), and rt.textures is an array. Lets a fullscreen-quad pass emit several screen-space buffers (e.g. color + velocity + id + a packed mask) simultaneously instead of re-rendering the scene once per buffer.
  - rare: Almost every tutorial does N separate passes or N separate render targets. The class was literally invisible-by-rename: it used to be WebGLMultipleRenderTargets (a different import), which made it feel like an exotic separate feature; since the merge most people never learned the count option existed on the RT they already use. Shines exactly when you already do fullscreen-quad GPGPU and want a second derived channel for free.
  - constraints: WebGL2 only (the project's WebGL2 detect already gates this; the WebGL1 fallback path can't use it — degrade to single-channel). Needs GLSL3 (#version 300 es) output declarations in the ShaderMaterial, which raw ShaderMaterial supports via glslVersion: THREE.GLSL3. No SSR/no-JS implications (canvas-only, stays inside the lazy 3D chunk and must not leak into reading routes). Does NOT need WebGPU. Merged into core at r162, so fully current in r184 — verified against the migration guide (r161→r162: 'WebGLMultipleRenderTargets has been removed. Use the new count property').
  - site seed: The reaction-diffusion / flow-noise background could emit a second 'velocity/gradient' attachment in the same pass it already runs, with effectively zero extra cost. The foreground physics RAF reads that low-res velocity texture (one readRenderTargetPixels of a tiny region, or sampled CPU-side) to give matter.js Tethers a faint ambient 'current' — the rope cards drift subtly in the direction the GPU flow field is locally moving. The background stops being purely decorative and starts gently steering the foreground, without a second simulation.
- **HalfFloatType feedback (ping-pong) render targets — RGBA16F instead of RGBA32F** — Setting type: THREE.HalfFloatType (not FloatType) on the two ping-pong WebGLRenderTargets that hold simulation state. Half the bandwidth and storage of full-float, with EXT_color_buffer_float-class support that is far more universally renderable-to on mobile/integrated GPUs than 32-bit float color buffers.
  - rare: Reflexively people reach for FloatType for 'accurate' GPGPU and never reconsider — exactly what this project does today (geometric-reaction-diffusion.tsx line 143-144 use FloatType). Half-float is the underused sweet spot: most stateful effects (reaction-diffusion, flow, fade-trails) don't need 23-bit mantissa precision, and 16F is renderable on hardware where 32F renderbuffers silently fail or fall back. Docs explicitly note 'half float may be faster on some hardware and occupies less space'.
  - constraints: Half-float has ~3-decimal-digit precision — fine for color/concentration fields, NOT for accumulating world-space positions over thousands of frames (drift). The existing scene's seed-and-display path would need a precision sanity check. Renderability still requires the WebGL2 path + EXT_color_buffer_half_float (essentially always present on WebGL2; verify on the no-WebGPU fallback). No SSR/no-JS concern (canvas chunk only). Not WebGPU-specific. Valid type confirmed in current docs' render-target type list.
  - site seed: Convert the existing reaction-diffusion ping-pong (and the audio-reactive beat-accumulator) from FloatType to HalfFloatType to halve VRAM/bandwidth on the laptops and phones that actually read the blog — buying headroom to run the background at a higher internal resolution OR to add the MRT velocity channel above without a frame-budget hit. Pure perf reclaim on an effect that already ships.
- **GPU color-id picking via a hidden id-pass + readRenderTargetPixels (userland pattern, not a core class)** — Render the scene a second time into an off-screen WebGLRenderTarget with each pickable object given a unique flat color encoding its integer id (override material / MeshBasicMaterial, no lighting, no AA). To hit-test the pointer you readRenderTargetPixels a 1x1 pixel at the cursor and decode the color back to an id — O(1) regardless of object count, and pixel-perfect on arbitrary shapes where a CPU raycast against bounding volumes is wrong or expensive.
  - rare: three.js ships NO core GPUPicker — it's the canonical 'famous technique with no official class', so it lives only in third-party repos (bzztbomb/three_js_gpu_picking, brianxu/GPUPicker) and most devs default to Raycaster and never discover it. It's the right tool precisely when raycasting is CPU-intensive 'depending on setup and number of objects' (per the picking examples).
  - constraints: Requires a full extra render pass to an RT (cost scales with scene, not pointer events) — cheap for this project's tiny scenes. readRenderTargetPixels is a GPU→CPU stall; do it on pointer events, not every frame. The y coordinate must be scaled by devicePixelRatio (a classic footgun). WebGL only — the WebGPU equivalent readRenderTargetPixelsAsync currently returns blank data (open three.js issue #31658, verify before any WebGPU port; irrelevant here since the project is WebGL2). No SSR/no-JS concern.
  - site seed: The foreground today is DOM divs positioned by matter.js, so picking is free via DOM events — BUT if a background scene ever renders interactive GPU geometry (e.g. the boids/voronoi cells become hover-targets, or a future canvas-rendered card field), color-id picking gives exact per-cell hit-testing the DOM can't. Concretely: hovering a voronoi cell in the background could PEEK the link whose 'territory' that cell represents — a Ladder interaction driven entirely on the GPU, no per-cell DOM proxy.
- **Material.onBeforeCompile — surgical GLSL injection into three's built-in materials (chunk string-replace hooks)** — A callback (shader) => {} on any built-in material that hands you the about-to-compile vertex/fragment source and a uniforms object, so you string-replace specific #include <chunk> shader-chunks to inject custom GLSL while keeping ALL of three's lighting/fog/tonemapping machinery. Lets you bend a stock material (vertex displacement, custom fragment masking, per-instance variation) without authoring a full ShaderMaterial from scratch.
  - rare: It is the deliberately-undocumented-feeling 'patch escape hatch' — fragile because it depends on exact chunk strings, so it's treated as advanced/scary. On WebGPU it's being superseded by TSL nodeMaterial hooks (colorNode/positionNode), which has led to the impression it's 'old' — but on the WebGL renderer this project is pinned to, onBeforeCompile is NOT removed and remains the only way to extend a built-in material short of rewriting it. The forum confirms it still ships; only the WebGPU path replaces it.
  - constraints: Brittle: keyed to three's internal shader-chunk names, which can change across releases — pin-locked here (three ^0.184), so safe as long as the pins hold, but re-verify on any three bump. Must set material.customProgramCacheKey when the injected code varies, or programs get wrongly cached. Memory note already learned in this repo: ShaderMaterial deep-clones uniforms — same care applies to uniforms you add in onBeforeCompile (mutate shader.uniforms.X.value, hold the ref). WebGL only / not WebGPU. Canvas-chunk only, no SSR concern.
  - site seed: Right now every background scene is a hand-written full ShaderMaterial on a fullscreen quad. For any FUTURE lit/3D background element (a single embossed glyph slab, a content-box 'shadow caster'), onBeforeCompile lets it inherit three's fog + tonemapping that the bespoke shaders re-implement by hand, while injecting just the flow-noise distortion in the vertex stage — less shader code to maintain, consistent tonemapping across scenes, and the monochrome brutalist palette stays driven by one set of injected uniforms.
- **Object3D.onBeforeRender — per-object, per-camera render-time callback for view-dependent uniforms** — A hook (renderer, scene, camera, geometry, material, group) => {} that three calls right before it draws THAT object, every frame, with the actual camera being used. The place to feed a mesh uniforms that depend on the live view/projection or on the object's just-resolved world matrix, or to swap a render target / toggle state for that one draw — without an outer useFrame that has to re-find the object.
  - rare: Overshadowed by R3F's useFrame, which most R3F devs use for everything; onBeforeRender is the lower-level, per-object, multi-camera-correct hook that fires inside the render loop with the real camera (matters when a scene is drawn from more than one camera/RT). Underused because in a single-camera app useFrame appears equivalent — it isn't once you have an off-screen pass.
  - constraints: Runs inside the render loop — keep it allocation-free and cheap (no new Vector3 per frame). Fires once PER camera the object is rendered with (a feature, but surprising). Pure runtime, no SSR/no-JS implication, no WebGPU dependency, present in core (stable, long-standing API). Lives entirely in the canvas chunk.
  - site seed: The audio-reactive scene needs the live beat phase and the cursor-repel lattice needs the live pointer in NDC right as it draws. Attaching onBeforeRender to those quads keeps their view-dependent uniforms updated at the exact draw moment even if the project later adds an off-screen pre-pass (e.g. the MRT velocity buffer above renders the same scene from a second 'camera'/RT) — the uniforms stay correct per-pass automatically, whereas a single useFrame would feed stale values to the second pass.
- **Reversed-Z depth buffer (renderer.reversedDepthBuffer) — the modern alternative to logarithmicDepthBuffer** — A renderer flag that flips the depth range so floating-point depth precision is distributed far more evenly across the view frustum, killing z-fighting at large near:far ratios — accomplishing what logarithmicDepthBuffer does but WITHOUT log-depth's per-vertex/per-fragment shader cost. logarithmicDepthBuffer is the classic 'big-range scene' fix; reversed-z is its cheaper successor.
  - rare: logarithmicDepthBuffer is the famous trick everyone reaches for (and then discovers it 'can degrade scene performance', per the active forum thread) — reversed-z is the newer, less-publicized flag that the three.js team explicitly recommends switching to 'when reversed z-buffer is supported... it accomplishes the same thing without the performance penalty'. Most content still teaches log-depth. Note the r119→r120 rename reverseDepthBuffer→reversedDepthBuffer is itself a 'why doesn't my flag work' trap.
  - constraints: Needs the perspective/orthographic depth path to matter — i.e. real 3D geometry with a wide near:far range. Today this project renders ONLY fullscreen quads / point clouds in 2D camera space with no depth conflicts, so reversed-z buys nothing YET; it only earns its keep if a depth-layered 3D scene is introduced. WebGL2 + float-depth support assumed; verify the exact flag name (reversedDepthBuffer, not reverseDepthBuffer) and renderer support at adoption time. Background-chunk only, no SSR/no-JS concern.
  - site seed: If the v2 'hero morph' ever escalates into a true depth-stacked 3D scene — e.g. the content box, the background field, and floating cards rendered as actual layered 3D planes at very different depths for a parallax-with-occlusion morph — reversed-z is the correct precision fix over log-depth, keeping z-fighting away at the morph's extreme depth spread without taxing the shader budget the cards' physics already competes for. File this as the 'reach for this, not logarithmicDepthBuffer' note for any future 3D-depth route.
- **Local clipping planes (renderer.localClippingEnabled + Material.clippingPlanes / clipIntersection)** — Per-material array of THREE.Plane objects that discard fragments on one side of each world-space plane, with clipIntersection toggling between union (clip outside ANY plane) and intersection (clip only inside ALL planes) semantics. A GPU-side scissor in arbitrary 3D orientation — slice a mesh open, reveal cross-sections, or mask rendering to a moving rectangular region defined by four planes.
  - rare: Clipping is one of those features buried in a single official example (webgl_clipping / webgl_clipping_intersection) that most projects never touch because their use cases are 2D-rectangular and CSS overflow/scissor already suffices. The clipIntersection union-vs-intersection distinction in particular is almost never used. Still fully supported (active official examples), just unglamorous.
  - constraints: Operates in WORLD space (planes don't auto-follow an object unless you transform them each frame). Requires renderer.localClippingEnabled = true. Clipped fragments are discarded, not depth-tested away, so heavy overdraw still costs. WebGL renderer feature (verify exact clipping support if ever porting to WebGPU). Canvas-chunk only, no SSR/no-JS implication. Confirmed present in current docs/examples.
  - site seed: The 'content box' registers its four edges as static physics walls already. Mirror those same four edge coordinates as four clipping Planes on any GPU element so a background/canvas effect can be made to render ONLY within (or only OUTSIDE) the content box's live rectangle as it scrolls/resizes — e.g. the flow-noise field bleeds across the whole viewport but gets cleanly clipped to a halo just around the reading surface, or a PEEK preview card rendered on the GPU is sliced exactly to the box edge as it morphs in. One source of truth (the box rect) drives both physics walls and the visual clip.
- **MeshDepthMaterial / customDepthMaterial — overriding the depth-pass shader independently of the color pass** — An object's customDepthMaterial lets you supply a SEPARATE material used only when three renders that object into a depth/shadow target, distinct from its visible material. The mechanism that makes alpha-tested foliage cast correct cut-out shadows, and that lets a vertex-displaced or procedurally-discarded surface have its silhouette match in depth-derived effects (shadows, depth-based fog/DOF/SSAO masks).
  - rare: Deeply hidden — it only matters once you both (a) modify geometry/visibility in a vertex/fragment shader AND (b) consume a depth pass; miss it and your custom material looks right but casts a wrong-shaped shadow or reads a wrong depth, a baffling bug most people never trace to 'the depth pass uses a different material'. Almost no tutorial mentions it because most scenes never displace vertices or alpha-discard.
  - constraints: Only relevant when something actually renders the object into a depth target (shadow map, or a manual depth pre-pass for a depth-driven post effect). Pure overhead otherwise. Must keep the custom depth material's vertex transform in lockstep with the visible material's — duplicated logic, a maintenance tax. WebGL core feature, stable; no SSR/no-JS concern; not WebGPU-specific. (verify the exact customDepthMaterial property path against r184 if used in a shadow context, since shadow internals shift between releases.)
  - site seed: Only earns a place if chaipalaka adds a depth-driven effect — e.g. a soft depth-based vignette or 'page-shadow' where the content box and floating cards cast a faint contact shadow onto the background to sell the gwern×physics layering. If those cards are GPU-rendered planes whose silhouette is shaped by a fragment discard (rounded corners, torn-paper edge), customDepthMaterial is what makes the cast shadow match that torn silhouette instead of showing a hard rectangle — the difference between a convincing and a fake depth layer. Park as a dependency of any future depth/shadow route, not a standalone build.
